# 演化机制

> 本规程**在使用中自己长大**：每次审阅都可能撞到"下次还会遇到"的东西，把它沉淀回 `references/`。
> 但**无约束的自我修改会让规程腐烂成日志**——所以准入、格式、告知三者缺一不可。

---

## 1 · 触发时机

**每次审阅收尾（写报告时）固定自问三句**：

1. 这轮有没有撞到**之前没记录过的**缺陷形态？（→ `03`）
2. 有没有撞到**之前没记录过的**工具链 / 环境坑？（→ `04`）
3. 有没有发明**之前没有的**探针手法、对拍方法、闸审计套路？（→ `01` / `02` / `06`）

三问全否 ⇒ 本轮无演化，报告里写"本轮演化：无"。

> 不要为了"有产出"硬写。**零演化是正常结果**。

## 2 · 准入判据（三条全中才写）

| # | 判据 | 自检问法 |
|---|---|---|
| 1 | **可跨批次复现** | "这是这一次的偶发，还是下次换个批还会遇到？" |
| 2 | **有明确判据或查法** | "我能写出一句'怎么查'吗？写不出就是还没想清，别写。" |
| 3 | **对下一次有可操作价值** | "下一个人读到这条，能少走一段弯路吗？" |
| 4 | **实例写得出「不含当时数字」的版本**（2026-10-02 补） | 「把里面的测试数 / 日期 / 批次号全删掉，这条还站得住吗？」站不住 ⇒ 你记的是**现场**，不是**形态** |

**任一条不中 ⇒ 不写。**

## 3 · 明确禁止写入的内容

| 禁止 | 例子 | 为什么 |
|---|---|---|
| **一次性现场快照** | "本轮 601 = SAME 596 / KNOWN 5"、具体 commit 哈希、某批文件数 | 下次跑就不一样，写进去等于埋漂移 |
| **一次性测量值**（2026-10-02 补） | `34/34 全绿`、`PASS 55 / FAIL 0 / 豁免 3`、某条目的当时条数 | 同左侧，且**数字最容易被顺手抄进实例**——要留的是「形状」（`70 任务 → 28 任务` 这类对比关系），不是「当时的绝对真值」 |
| **相对时间叙事** | "上轮""本批""此前""我第一版踩了" | 对次日或对 clone 的人无意义 |
| **当次审阅的结论本身** | "P1：X 函数少一个 `\n`" | 那是报告的内容，不是规程的内容 |
| **第二人称日记** | "我踩过""我因此误判" | 改成无人称的形态陈述 |
| **未经核实的猜测** | "可能是因为编译器……" | 规程里只放实证过的东西 |

**改写方向**：把"这次发生了什么"改写成"**这类事怎么判、怎么查**"。

```
✗ 本轮 getchar 每行少一个 \n，实测 n=3 vs n=2
✓ 行的边界形态：一侧每行含尾换行、另一侧剥掉 ⇒ 逐字节读的接口会少一个 \n。
  查法：造 "ab\ncd\n" 输入，比 getchar 计数。
```

## 4 · 各文件的追加格式

**保持目标文件的既有结构**，别另起一套。

- `03-缺陷形态清单.md`：按 A（锚）/ B（分叉）/ C（死面）/ D（闸）/ E（文档）/ F（工具）分类。**能归入既有类就归入**；确需开新类时，在文末"追加约定"处说明理由。每条格式：
  ```
  ### X n · <形态名>
  - **判据**：…
  - **查法**：…
  - **实例**：（可写项目内真实位置**与可复现判据**——一条命令 / 一段注入写法 / 一个 `文件:行`；**不写**具体 commit / 批次 / 测试数 / `PASS n / FAIL m`）
  - **处方**（可选）：…
  ```
- `04-工具链与踩坑.md`：表格一行（坑 / 表现 / 处置）。新坑先判断是"确定性行为"还是"偶发"——偶发的写清触发条件。
- `01` / `02` / `06`：按各自现有小节风格追加，**不要破坏编号**（编号被本文件与其他文件交叉引用）。

## 5 · 变更纪律

1. **只追加，不改写既有条目。**
   - 既有条目被证明写错了（不是"补充"，是"错"）⇒ **先问用户**，得到确认后再改，并在该条后加 `> 纠正（来源：…）`。
   - 单纯"补一个新例子"不算纠正，直接追加。
2. **改完必须显式报告**：在当轮回复里列出【改了哪个文件 + 加了什么】，并在报告结构第 4 节"本轮演化"里重复一次。
   - **静默修改视为违规**——用户无法察觉的自我修改，比不修改更糟。
3. **每次演化追加一行到 `references/07-演化日志.md`**（格式见下）。
4. **一次审阅的演化总量**建议不超过 5 条。超出说明你在把当轮报告塞进规程，回去按 §3 过滤。
5. **禁止顺手重构**：演化时不要重排章节、改标题、统一措辞——那些要单独提，别混在沉淀里。
6. **合并是「追溯性整理」，不是默认动作**（2026-10-02 补）：同族触发面**优先并入既有条目**（做成子项 / bullet）而不新开编号（正例：`03` 的 `A1` 六个子项、`D8` 四条 bullet）；确需**合并既有条目**时须**用户拍板**，且**判据零丢失**（保内容、压形态，只去重复表述与过期数字），合并后在 `07` 追加一行说明哪几条并入了哪条。

## 6 · 演化日志格式（`07-演化日志.md`）

```markdown
| 日期 | 触发 | 落点 | 内容 |
|---|---|---|---|
| YYYY-MM-DD | 审阅某批时撞到 X | 03 · B10 | 新增"形态名"：判据 / 查法 |
```

- **触发**：一句话说清是什么事让你决定写它（这批做了什么，不写 commit）。
- **落点**：文件 + 条目标号。
- 日志**只追加**，同样禁止改写历史行。

## 7 · 为什么要"必须告知"

- 规程是**多人多 agent 共用**的判断依据。一次静默改动，可能让别人基于"以为没变"的规程继续做事。
- 用户是本规程的**最终责任人**：他有权知道判断依据变了什么。
- 演化本身也要**可回溯**——出了问题时，得能查到"是哪次审阅把这条规则加进去的"。

## 8 · 演化与"不改代码"的边界

- 演化**只改本 skill 目录内的文件**（`SKILL.md` + `references/`）。
- **不得**以"演化"为名改动仓库内的任何其它文件、`AGENTS.md`、或 CI 配置。
- 本规程若需要**仓库内**同步（如 `AGENTS.md` 的路由行）⇒ 那属于**仓库变更**，按仓库纪律走（先问用户）。
