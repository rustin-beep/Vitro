## 0. 结论摘要

1. **Rust 侧的多真相来源问题已实质收口，但"收口"的判据不覆盖跨语言**（§2.3）。`compute_type_size` 在 Rust 侧确为单源 + 三处委托〔实测〕，MoonBit 侧同样正确〔实测〕——这是值得登记为正面模式的资产。但迁移使每个"单源"都多了一个跨语言孪生，而 `三语化整备审计计划.md` §1 判为"✅ 已收口"的 L1，其判据（R3 审计）**只检查仓内同语言重复，不覆盖跨语言同步**。
2. **最需要优先处理的结构性问题是"对拍锚锁死了重构空间"**（§4.1）。A 级 code 段逐指令对拍 + 槽位策略 v1 逐位兼容，使任何"输出可观测"的内部重构必然全红——这就是 `temp_slot` 固定 4 槽（3 起同类 bug、2026-09-06 审查报告建议一次性根除）至今未启动的真实原因。MoonBit 侧已提出 `SLOT_STRATEGY_VERSION` 常量分档，**Rust 侧没有同步**，否则该病灶会被固化进新实现。
3. **`native/src/` 是上帝包**（§2.1）：14,998 行 / 57 文件承载六种不同生命周期，且**它自己不作为任何 crate 的依赖存在**，因此无独立版本化能力。而 MoonBit 侧已按 L0–L9 切好 10+ 包——**活跃区（计划中的新实现）的包划分反而比冻结区的 Rust 侧更干净**。
4. **"加一门语言要不要改核心"这个问题，当前答案是"要"**（§2.4）。C# 前端需新增 `csharp/{lexer,parser,typeck,codegen}` 四包。语言定义（语法/诊断/算法模板/容器）仍是 md 文档 + 散装资产，不是引擎读取的数据源。
5. **JIT 决策被"单出口"假设掩盖**（§2.5）。F-3 裁定"JIT 不搬"的依据是"宿主 V8 自带 JIT"——该依据**只对 wasm-gc 出口成立**；对 native 出口不成立（门 1 实测 JIT 相对解释器 8.8×：55ms vs 512ms）。

## 2. 架构设计

### 2.1 【P1】`native/src/` 上帝包，且不参与依赖图

**证据〔实测〕**：
```
crates/vitro_algorithm_steps  2,273 行   crates/vitro_parser    4,879 行
crates/vitro_ast              1,679 行   crates/vitro_runtime   2,043 行
crates/vitro_codegen          6,286 行   crates/vitro_shared      372 行
crates/vitro_cpp_frontend       186 行   crates/vitro_typeck    8,834 行
crates/vitro_lexer            3,639 行   crates/vitro_vm        8,863 行
src/                         14,998 行  ← 57 文件，六种职责
```
`native/Cargo.toml` 中根 package `vitro_native` 依赖全部 10 个 crate，而**没有任何 crate 依赖它**。`src/` 下并存：`capi/`（对外契约）、`session_api.rs`（会话语义中立层，1,132 行）、`unified/`（时间旅行，含 `stream/`、`trace_analyzer/`）、`engine/`（含 `completion/`）、`compiler/`（静态分析）、`diagnostics/`（含 `error_catalog/`）、`shared/`、`bin/`。

**为什么是问题**：这六种职责的**变更频率与稳定性等级完全不同**——`capi` 是对外承诺（应极少变）、`diagnostics/error_catalog` 是内容数据（频繁变）、`unified` 是已被自身审计标为"重构区"的子系统（`三语化整备审计计划.md` §5.0）、`compiler/` 是分析算法（快迭代）。放在同一个 package 里意味着：**无法独立版本化、无法独立发布、无法给消费者单独依赖"只要编译管线不要教学层"。**

**外部惯例**：rust-analyzer（~200k 行）用扁平 `crates/*` 布局，32 个 crate；matklad 在《Large Rust Workspaces》中明确"**10k–1M 行项目扁平结构最合理**"，理由是 cargo 的 crate 命名空间本就是扁平的，嵌套树没有任何收益。Vitro 在 78k 行区间，且**MoonBit 侧已经按 L0–L9 把包切好了**——活跃区比冻结区更规范，这个反差本身就是改进信号。

**建议**：把 `src/` 按 MoonBit 的 L0–L9 对齐切为 crate，根 package 只保留 `bin/` 与 re-export：
`crates/vitro_session`（session_api）、`crates/vitro_unified`（统一模式/时间旅行）、`crates/vitro_analysis`（compiler/ + diagnostics/）、`crates/vitro_gateway`（capi + serve 协议）。**验收判据：`vitro_native` 的 `[dependencies]` 只剩 `bin` 所需的最小集，且根 package 行数降到 1k 以下。**

### 2.3 【P2】"L1 已收口"的判据需要扩范围

`三语化整备审计计划.md` §1 根因分层表判：**L1 结构层"同一概念多真相来源" → ✅ R 系列已收口（R3 审计归档，判据未再触发）**。

**本次实测确认 Rust 侧确实收口了**（这是正面结论，见 §3.1）。但迁移产生了**跨语言版本**：每个 Rust 单源在 MoonBit 侧都有一个孪生实现，同步义务是人工的（`moonbit/AGENTS.md` 纪律第 4 条"照搬不私改：逐字照搬；发现 oracle 现状可疑**登记不修正**"）。

**判据缺口**：R3 审计检查的是"仓内同语言内同一概念是否多份实现"。它**不覆盖"同一概念在两个语言里各有一份、且只能靠人工保持同步"**这一新形态。项目的检测手段是 A/B/C/D 级差分锚点，但锚点是**行为级**的——`三语化整备审计计划.md` §2 的 M5「行为等价 ≠ 语义正确」正是这个缺口的同构表述，只是当时还没跨语言。

**建议**：把 L1 的判据扩展为"**单一真相源清单**"，并给每条登记：① 单源位置（两侧各一）；② 同步方式（人工/生成器/无）；③ 检测锚点级别。清单本身入版本控制，新增单源必须登记。可复用 `gen_diag`／`gen_host_route` 的"落款 sha + `-check` 幂等"三件套做成清单校验器。

### 2.4 【P1】扩展性判据："加一门语言要不要改核心"——当前要改

`三语化整备审计计划.md` §5.0 与 `CSharp前端引入计划.md` 显示，C# 前端需要新增四个包（`csharp/{lexer,parser,typeck,codegen}`），并在 VM 状态机里预置三个执行状态（handler 栈 / 异常寄存器 / UNWINDING）。C++ 侧曾经的寄生债（`is_cpp_mode` 46 处亲证散落、`typeck/cpp` 预留位）也是同一模式。

**根因**：语言定义仍以两种非数据形态存在——
- **文档形态**：`docs/current/03-语言子集/{C语言子集规范,C++子集规范,CSharp前端引入计划}.md`
- **散装资产形态**：`templates/`（`source.c` + `meta.yaml`）、`native/runtime_libc/`、`vitro_cpp_frontend`（仅 186 行）

**但项目已具备数据驱动的基础设施**：`libc` 是 builtin 签名单表（57 条）、`containers` 规划为 JSON 数据驱动、`diag` 的 137 臂由 `gen_diag` 生成、opcode 是全表、host 路由 110 对由 `gen_host_route` 生成。**方向是对的，但"语言子集定义"这一层还没纳入。**

**建议（本轮最高杠杆的一条）**：把语言子集定义抽成**机器可读的描述文件**（语法产生式/关键字表、诊断码到语言的映射、算法模板元数据、容器与 BCL 类型表），由引擎按表驱动；判据：**"加一门语言 = 加一份数据 + 加一张表"，而不是"加一个 crate 族"。** Neovim 加一门扩展语言不需要改 C 核心，这是它最值得抄的一点。

### 2.5 【P1】JIT 决策被"单出口"假设掩盖

`MoonBit迁移总计划.md` F-3 裁定"**JIT 倾向不搬**"，依据摘要为"宿主 V8 自带 JIT 边际缩水"。**该依据只对 wasm-gc 出口成立**：S6 裁定"不搬"时隐含了"只保留一个出口"这个前提（同文档 §11 全量切换）。

但对保留 native 出口的情形（`README` 仍将 native cdylib/C ABI 列为出口 1，且 F-4 明确 Go 驱动层"v1 保留"），JIT 的收益是实测的：**门 1 实测现役解释器 512ms / JIT 55ms = 8.8×**（而 MoonBit 迷你 VM native 81ms / wasm-gc·V8 156ms）。同时 `#![forbid(unsafe_code)]` 覆盖核心 crate 使机器码 JIT 结构性不可能（`jit_templates.rs:3` 自陈"无法动态生成机器码"）。

**建议**：把 JIT 决策**按出口分别裁定**（native 出口 / wasm 出口），而不是一次裁定。若最终采纳"native cdylib + wasm-gc 双出口"，则 native 侧的 JIT 议题需要重新评估——否则会用一个出口的结论去否定另一个出口的收益。

## 4. 扩展性与重构空间

### 4.1 【P1，本次最重要】A 级对拍锚锁死了重构空间

**机制**：A 级锚点之一是"**字节码产物 code 段逐指令**"，其前提是"**槽位策略版本化**"——现行策略为 v1，MoonBit 侧另有评审纪律"**A 级 code 段逐位 diff 以现行槽位策略为前提**"（`moonbit/AGENTS.md` 包清单 `codegen` 行）。

**后果**：任何改变 code 段输出的内部重构 → A 级对拍**必然全红** → 无法区分"重构引入缺陷"与"预期形状变化"。

**这解释了三个已登记但未根除的病灶为什么悬置**：`temp_slot` 固定 4 槽（**3 起同类 bug**，2026-09-06 审查报告 §7.2-7 明确建议"一次性根除"）、`next_local_offset` 只增不减、以及"槽位泄漏 × ARC 插桩密度"的共振风险（`三语化整备审计计划.md` §0-5）。它们全部落在 `code 段可观测` 的范围内。

**已有的部分解**：MoonBit 计划已提出 `SLOT_STRATEGY_VERSION` 常量分档（"v1 常量已落 codegen 包"，v2 批计划"补挂 8 条回归并以常量分档"）。**但 Rust 侧没有同步这套分档机制**。

**建议（优先级最高，因为它决定其他重构是否可做）**：
1. **Rust 侧同步 `SLOT_STRATEGY_VERSION`**，把 A 级对拍改成"**同版本内逐位相等 + 跨版本按语义等价判定**"。
2. 为 v2 预留**形状白名单**（显式列出"哪些 code 段差异属预期"），并保证"白名单为空时不得绿"（项目已有"空集不得绿"纪律可直接沿用）。
3. 顺序上：**先做分档机制，再动槽位病灶**。否则病灶会被原样搬进 MoonBit 侧并永久固化——`moonbit/AGENTS.md` 的"槽位策略 v1 逐位兼容"已经把这条路径写明了。

### 4.2 【P2】接口面生成层缺失（"绑定层厚"的正解）

现状：`capi` 手写、Go shadow 手写。对照 Neovim——`api_metadata` 喂 `gen_api`，一次生成 C 侧 dispatch 与各语言 client 绑定，绑定不锁定客户端语言。

**项目已有现成的成功模式可复用**：`gen_diag`（137 臂码表）与 `gen_host_route`（110 对路由表），且都有"**落款 sha + 内置 `moon fmt` + `-check` 幂等**"三件套纪律与 CI 门禁。

**建议**：以同一模式新增 `gen_capi_bindings`，输入 `native/include/vitro_capi.h` + `docs/spec/STEP_PAYLOAD_SCHEMA_V0_1.md`，输出 Go / Python / .NET 的绑定骨架。**这能把手写绑定变成生成问题，且完全不需要换语言、不需要动出口。**

### 4.3 【P2】Rust 侧缺"接口面快照"

MoonBit 侧 `pkg.generated.mbti` 入版本控制（已是纪律），但 Rust 侧无等价物——crate 的公共 API 变更不会在任何 diff 里显现。建议引入 `cargo public-api`（或自写 emitter）生成 API 快照并入库，与 `.mbti` 对称。

**关于"不同语言的写作风格与惯例"的结论**：选 Rust/MoonBit 而非 C 的**主因不是性能，是"编译期可判纪律"**：
- C 的 `switch` 不强制穷尽，而本项目有 137 诊断码 / 132 opcode / AST 三族**持续增长**的枚举，"增删变体必须让全仓编译红"这条纪律在 C 里**零编译期支撑**。
- Zig 的 `union(enum)` + `switch` **强制穷尽**（这条合格），且 comptime 极适合生成项目那三套码表；但**每个涉及分配的函数需穿 `Allocator`、无 owned String**，对"字符串密集的编译器"是实打实的样板税——这与你前几轮的判断一致，本次维持。
- MoonBit 的穷尽性由 `moon check` 默认强制（F7 删臂实验 exit 127），且**标准库/工具链仍在演进**（官方 beta 承诺语法稳定、明言 stdlib 与工具链继续改进；本机实测仍在 `moonc 0.10.13` 线）——这正是项目 29 条陷阱的来源层。

## 9. 框架演进方案（回应"该如何更改现在的框架"）

### 9.0 先说结论：不完美的不是"框架选错"，是"边界没切干净"

现有框架事实上**已经是**分层 + 多语言，而且分工是对的（§6）。它缺的三样，**没有一样是换架构能解决的**：① 边界切分（§2.1 上帝包）；② 生成层（§4.2 绑定与接口面）；③ 冻结层（§4.1 对拍锚分档 + 协议冻结）。

### 9.1 三个选项的裁决

**选项 A：Neovim 式多语言协作 —— 已经在做，继续做。**
需要先澄清一个误解：**Neovim 的多语言是"分层"（C 核心 / Lua 扩展层 / **任意语言**的 client），不是"同一份计算写两遍"。** Neovim 从不把同一个 compute 实现两次。所以"像 Neovim"的正确动作是：分层（已有）+ API 由元数据生成（缺）+ 协议冻结（缺）。它**不要求、也不建议**把编译流水线切给不同语言。

**选项 B：月兔全栈 —— 是当前路径。我认为最终必须二选一（全栈 Rust 或全栈月兔），不要混。**

**选项 C：分而自治（建语言中间量 / 统一前端 / 后端多语言协作）—— 初判为反模式，2026-09-21 已撤回并重写（见 §9.8）。** 原判据是"重复提供独立性"，但该项目的人机协作模型是**抽卡式**（人发任务 → AI 依训练分布生成 → 人靠探针与审阅找缺陷，而非逐行审代码），且项目自陈"眼见不一定为实（假绿/假红）"。**在该模型下，两份 AI 生成的实现是同分布的，独立性本就微弱——原始判据建立在一个不存在的资产上。** 修正后的分析见 §9.8。

### 9.2 【已撤回·保留两点残余有效性】原"反模式"论证

> **撤回说明（2026-09-21）**：本节原判"分而自治是反模式"的核心论据是"重复提供独立性"。该论据在人机协作的**抽卡模型**下不成立——两份实现若都由 AI 依同一训练分布生成，则**同分布**，独立性本就微弱。原判据建立在一个不存在的资产上。**修正后的完整分析见 §9.8。** 下文仅保留两点在修正后仍然有效的观察。

**残余有效观察 1：验证强度的真实分层。** 下表的结论不受撤回影响，而且正是撤回的依据——

| 对照对 | 独立性 | 能抓什么 |
|---|---|---|
| Clang golden ↔ Vitro | **真独立**（不同实现、不同作者） | 设计缺陷 + 实现缺陷 |
| Rust ↔ 月兔 | **转写**（`照搬不私改`；发现 oracle 可疑**登记不修正**） | **只抓翻译 bug，不抓设计 bug** |

**残余有效观察 2：接口自身缺陷不可自检——这条依然成立，但补救方式与我原判不同。**

原论证的三条逐项复核如下：

| 原论证 | 裁决 | 复核结论 |
|---|---|---|
| ① "两遍"退化为"一遍 + 一个接口"，对拍独立量消失 | **撤回** | 该"独立量"在抽卡模型下本就微弱（同分布） |
| ② 接口两侧都由我们写 ⇒ IR 自身设计缺陷两侧同时成立、互相印证 | **成立** | **这是分而自治的真实风险**，但补救不是"不切分"，而是：IR 必须冻结 + 必须挂**外部对照**（Clang/dotnet/Roslyn 的真值不得经过这条 IR 的重述） |
| ③ 跨语言切点引入的序列化层会掩盖字节级差异 | **事实错误，撤回** | 项目**已经证明跨边界可以逐字节精确比对**：`canonicalize`（Go，键排序/转义/缩进固定，fail loud）+ A 级 code 段逐指令 + 备忘录式"bundle 禁逐字节、解析后结构化比对"（F9）。只要序列化是**规范化的**，切点不掩盖差异——**规范化序列化本身就是这个项目已有的基础设施** |

**修正后的判断**：切分本身不破坏可比性（③ 被项目自身实践否证）；真正的风险是 ② —— **IR 成为"两侧都由我们写、因而不可自检"的新层**。因此切分的**前置条件**是：IR 冻结 + IR 必须有外部真值对照（见 §9.8）。

**契约现状（不变）**：`E4 typed_ast 投影` + `CompileOutput` 13 字段 + `canonical dump` + `docs/spec/STEP_PAYLOAD_SCHEMA_V0_1.md` 已存在。缺的是"冻结"与"生成器"。

### 9.3 Oracle 该选什么语言：先把两个角色拆开

"oracle"这一个词现在盖住了两种完全不同的东西：

| 角色 | 现在是谁 | 独立性的要求 | 裁决 |
|---|---|---|---|
| **真值源**（行为基准） | Clang / dotnet / Roslyn | **必须完全外部**，绝不能自己写 | **不动**——这是项目最值钱的资产 |
| **归一化 + 驱动**（对拍管道） | Go，10,767 行，`shadow_verify.go` capi 直调 680 用例 | **不得与引擎共享代码** | **保持 Go** |

**为什么保持 Go**：它的任职资格是"**和引擎不同**"，而不是"它适合写引擎"。Go 与 Rust/月兔都不共享代码，满足独立性；`sort.Strings` 是字节字典序，与 Go canonicalize 的归一化口径一致（`moonbit/AGENTS.md` #29 已记录此点）；diff / 排序 / 子进程编排正是它的强项；680 用例已在跑，没有替换理由。

**但要修正一个认知**：**Go 不是 oracle，它是归一化器。** 真正的 oracle 是 Clang / dotnet / Roslyn。这个区分重要，因为：

> **"Rust 冻结为 oracle"这个说法需要精确化。** Rust ↔ 月兔 的差分是**转写级**的——只覆盖"搬迁正确性"，不覆盖"设计正确性"。它的价值随迁移完成而**衰减到零**（没有新代码可搬时，就没有对照物了）。**它不是可以长期依赖的验证层。**

所以"永久保留 Rust 当 oracle"**不是一条可持续的架构路线**。可持续的是**外部真值链 + 独立归一化器**——这两样与引擎用什么语言无关。

### 9.4 "等月兔迭代完毕，利用残躯"——拆成两句

- **代码不可复用**：跨语言没有代码复用的路径。Rust 的 77,771 行在迁移完成后是**历史参照**，不是可拆件。（这正是 §0.1 那两个 tag 的意义：把它从"活代码"降级为"可检索归档"。）
- **资产可复用，而且大多已经语言中立**——这才是"残躯"里真正该保住的东西：
  `native/tests/cases/` 的 C 语料与 C++ 语料、`runtime_libc/` 的 C 存根、`templates/`、`docs/spec/` 的 schema、`include/vitro_capi.h`、`reports/facts.json` 台账、`scripts/` 的 CI 与归一化工具。
  **判据：迁移完成时，"保留清单"里不应有一行是 Rust 或月兔专有的源码。**

### 9.5 工具链复杂的问题，正解不是"减少语言数"

工具链数量应该靠**"让引擎只有一种实现语言"**收敛，而不是靠"把流水线分给多语言"——因为外围各角色不可替代：

- 真值源必须外部（Clang / dotnet / Roslyn）→ **不可省**
- 归一化器必须独立于引擎（Go）→ **不可省**
- 宿主必须贴平台（Node / 浏览器 / Wasmtime）→ **不可省**

**能省的只有"引擎的第二个实现"**，而当前正在付两份引擎的钱（Rust 77.8k + 月兔 60k 行）。

> **因此：工具链复杂度的收敛点 = 迁移完成 + Rust 从"活代码"降为归档 tag。** 这两个 tag 已于 2026-09-21 建立〔实测〕：
> - `moonbit-probe-archive` → `917251e`（2026-09-18）—— 8,022 行探测档案
> - `moonbit-probe-consolidation` → `c0b642f`（2026-09-18）—— 浓缩点
>
> **注意（实测坑）**：本环境下**带斜杠的 tag 名会静默失败**——`git tag -a archive/xxx <ref>` 返回 `rc=0` 但 ref 不创建（沙箱无法创建 `.git/refs/tags/xxx/` 嵌套目录）。最终采用无斜杠命名，与既有 6 个 tag 的命名风格一致。**标签目前仅在本地，需 `git push origin <tag>` 才发布。**

### 9.6 那到底该怎么改：五步，前三步现在就能做

| 序 | 动作 | 依赖 | 可机判判据 |
|---|---|---|---|
| 1 | 单源清单 + 跨语言单源纳入 L1 判据（§2.3） | 无 | 清单入版本控制 + `-check` 幂等校验器 |
| 2 | `SLOT_STRATEGY_VERSION` 分档机制（§4.1） | 无 | 跨版本白名单为空时不得绿；注入形状变更能证红（J9 同款） |
| 3 | `gen_capi_bindings` 生成器（§4.2） | 无 | 至少生成 Go 绑定并替换手写版；落款 sha + 幂等三件套 |
| 4 | Rust 侧按 L0–L9 重切 crate（§2.1） | **建议在 2 之后**——否则重切会撞 A 级全红 | 根 package `[dependencies]` 为最小集；行数 < 1k |
| 5 | **语言决策：以 S6 为决策门** | S6 完成 | 门 1 条件 A（1k×1k 对照 512/55ms 双基线）+ 门 3 集成版 |

**第 1–3 步对"全栈月兔"与"回退 Rust"两种结局都成立**，是纯收益、零后悔的动作。

### 9.7 语言决策的正确时点是 S6，不是现在

这是本章最实际的一条建议：

- 迁移进度 S0.5–S5 已完成，**剩下的 S6（memory / host / vm）恰恰是月兔语言事实咬得最狠的一层**——F1（`Int` 静默回绕、core 无 checked API ⇒ 每条算术指令都要应用层显式检测）、F3（内存载体密度 1:3.8，1MB 载体定案）、F4（wasm-gc 栈预算 854 层 vs native 1005）。
- 也就是说：**已完成的都是低风险切片，未完成的才是高风险切片。** 在 S6 之前停下 = 付完安全部分的钱，恰好在风险最大的地方止损；**在 S6 之后判定，才是拿到了真正的证据。**
- 而 S6 的验收线**项目已经定义好了**（门 1 条件 A 性能锚 + 门 3 集成版快照往返），**不需要新增任何工作就能把"继续 / 回退"变成一次可判定的决策。**

> **结论：现在不拍语言决策，把 S6 做完再拍。** 当前该做的是 §9.6 的第 1–3 步——它们与语言决策解耦，且两种结局都受益。

## 9.8 三层的落地处理 + 分而自治修正案（2026-09-21 追加）

### 9.8.0 判据替换：从"能否重复"改为"探针面"

本项目的人机协作模型是**抽卡式**：人发任务 → AI 依训练分布生成 → 人靠**探针与审阅**找缺陷（而非逐行审代码），且项目明确声明"眼见不一定为实"（假绿 / 假红并存，见 `三语化整备审计计划.md` §2 的 M1–M9）。

**在该模型下，架构的验收判据不是"能不能重复实现"，而是三条**：

1. **探针面够不够多**——每个新增出口/消费者/锚点都是一条独立探针路径；
2. **探针够不够便宜**——生成物 > 手写物；结构化台账 > 自由文本；
3. **探针够不够持久**——冻结的协议使旧探针长期有效；未冻结的协议使探针随实现漂移而失效。

这三条正是 §9.8.1–9.8.3 三层的验收标准。

### 9.8.1 边界切分：先断言，再从外圈往里切

**第 0 步（零风险，先做）**：新增 CI 依赖方向断言脚本——扫描 `native/src/` 与各 crate 的 `use`，输出有向图，断言 ① 无环 ② **诊断/教学层不得被编译管线依赖**。纯读、不改代码，但能在动刀前暴露循环依赖。

**第 1–5 步（按易切度排序，每步独立可验收）**：

| 顺序 | 新 crate | 来源（实测行数） | 为什么这个顺序 |
|---|---|---|---|
| 1 | `vitro_diagnostics` | `src/diagnostics/`（含 `error_catalog/`） | 内容数据，与管线单向依赖，最干净 |
| 2 | `vitro_analysis` | `src/compiler/{cfg,data_flow,intent,algorithm_detector}`（2,900 行） | 纯消费者，只读 AST |
| 3 | `vitro_unified` | `src/unified/`（含 `stream/`、`trace_analyzer/`） | 已被自身审计标为重构区，独立才好动 |
| 4 | `vitro_session` | `src/session_api.rs`（1,132 行） | capi 与 serve 共用的语义中立层 |
| 5 | `vitro_gateway` | `src/capi/` + serve 协议 | 对外契约，应最少变动 |

根 package 最后只剩 `bin/` 与 re-export。**判据**：`cargo tree -p vitro_native --depth 1` 一眼可读；根 package 行数 < 1k。

**前置依赖**：必须在 §9.8.3 的"对拍锚分档"之后做——切 crate 本身不改 code 段，但若顺手动了模块内部结构，就会撞 A 级全红；分档机制未就位时，无法区分"重构引入缺陷"与"预期形状变化"。

**顺带清理**：`src/compiler/ast.rs`（116 行死文件，永不编译）应在第 2 步一并删除（§2.2）。

### 9.8.2 生成层：它是抽卡模型的"收敛器"

**为什么这一步对抽卡模型价值最大**：手写绑定意味着**每次抽卡都可能偏**；生成绑定把 AI 的发挥面压缩到**元数据一处**。这是用生成器对抗人机协作的方差——比"审阅得更仔细"有效得多。

**做法（复用已验证的 `gen_diag` / `gen_host_route` 三件套）**：

1. **先抽元数据**：把 `native/include/vitro_capi.h` 从"手写声明"改为机器可读描述 `capi_manifest.json`（函数名 / 参数 / 返回 / **所有权语义** / 线程模型 / ABI 版本），头文件本身降为生成物。
   > 为什么"所有权语义"必须进元数据：`tests/capi_string_ownership_contract_test.rs` 的存在，说明这类契约最容易在抽卡时丢失。
2. **生成物**：① C 头文件 ② Go 绑定骨架 ③ Python 绑定骨架 ④ .NET P/Invoke 骨架 ⑤ `vitro_abi_version` 版本常量。
3. **三件套纪律**：落款源 sha256 + 生成流程内置格式化 + `-check` 幂等 + CI 防漂移。

**判据**：手写 Go shadow 的绑定部分被生成物替换；**版本变更时第三方消费者能只改版本号完成升级**（这是"承诺"的可机判形态）。

### 9.8.3 冻结层：对拍锚分档 + 协议冻结

#### (a) 对拍锚分档——解锁其余一切的前置

- Rust 侧补上 `SLOT_STRATEGY_VERSION`（月兔侧已有 v1 常量），A 级判定改**三态**：
  - **同版本** → 逐位必等
  - **跨版本** → 按**显式形状白名单**判语义等价
  - **白名单外差异** → 红
- **必须带证红**：注入一条形状变更，证明白名单机制能区分"预期"与"非预期"。理由即"眼见不一定为实"——**一个从未红过的检查，与一个坏掉的检查，在观测上无法区分。**
- 沿用既有"白名单为空时不得绿"纪律。
- **顺序**：分档机制 → 再动 `temp_slot`（挂上 8 条事故回归，v2 常量分档）。

#### (b) 协议冻结——含一个专门针对"假绿"的陷阱

| 冻结对象 | 现状 | 政策 |
|---|---|---|
| `vitro_abi_version` | 已有（2.1.0） | 只加不改 |
| `STEP_PAYLOAD_SCHEMA` | v0.1 | 只加不改 + 字段级冻结测试 |
| `IR`（若采纳 §9.8.4 切分，则新增） | 尚无 | 只加不改 |

**"冻结"唯一能被自动验证的形式**：CI 对每个已发布版本跑**冻结快照对拍**——取上一发布版本的 golden payload 喂当前引擎，断言新增字段可忽略、**删除或改名即红**。

> **⚠ 该测试最典型的假绿是：快照本身是拿当前实现生成的。** 必须写死纪律：**冻结快照只能来自上一个发布版本，入库后禁止重新生成。** 否则该测试会永远绿，而且绿得非常像真的。

### 9.8.4 分而自治修正案：它不是待建方案，是"现在停手"的样子

**关键事实认知**：分而自治**不需要新建**，因为两边都已存在——

- MoonBit 前端**已完成**（S1–S4：`ast` / `lexer` / `parser` / `names` / `libc` / `typeck` / `diag`）
- Rust 后端**已完成**且全绿（`codegen` / `runtime` / `vm` / `unified` / `session` / `capi`）

**当前迁移的动作实质是"继续替换 Rust 后端"，而不是"从零搭一个协作架构"。** 因此真实的三选一是：

| 选项 | 增量成本 | 真实税率 |
|---|---|---|
| ① 月兔全栈 | 续做 S6–S9 | 月兔生态/工具链风险；**S6 恰是风险最集中那层**（F1/F3/F4） |
| ② 分而自治 | **近零**（两侧均已存在） | **Rust 必须保持活跃，不能冻结** |
| ③ 回退 Rust 全栈 | 沉没已迁 60k 行 | 丢 wasm-gc；`#[forbid(unsafe_code)]` 挡机器码 JIT |

#### ②的真实税率（原报告该说而没说的一条）

C# 前端计划中，**后端要动三处**（ARC 插桩 / 异常映射 `trap→Throw` / 顶层语句入口合成）+ **VM 三状态**（handler 栈 / 异常寄存器 / UNWINDING）。若前端在月兔、后端在 Rust，则**每加一门语言、每加一个特性，都要同时动两种语言的交界两侧**。这才是 ② 的税，而非"丢失独立性"。

#### ②的更优变体：把切点从 `typeck→codegen` 挪到 `codegen→VM`

| 侧 | 语言 | 承担 | 理由 |
|---|---|---|---|
| 编译 | 月兔 | 前端 + **codegen** | codegen 是**语言特定性最强**的一层（每加一门语言都要改它）→ 加语言只动一侧 |
| 执行 | Rust | VM + memory + unified + session | VM 是**最热、最吃精确内存语义**的一层 → 性能与语义都稳（门 1 的 512ms 基线就是 Rust VM） |

**边界的产物项目已经有了**：`CompileOutput` 13 字段 + `canonical dump` + A 级 code 段锚——全项目**最成熟的契约**，且逐字节可比。

**决定性优势**：该切点**只在编译期跨一次，运行期全在 Rust**——单步、时间旅行、observer **都不跨边界**。而这条边界所需的三条契约，项目**早已冻结**：**槽位策略版本化 / 绝对 IP 跳转编码 / libc 固定索引**。即：项目已在无意中为这个方案做完了准备。

**该变体无法绕过的一个问题**：**浏览器侧那个运行时是谁？** 若浏览器要求单产物，则须有一个语言装下整个运行期；以 `codegen→VM` 切，浏览器里将同时存在月兔的 wasm-gc 模块与 Rust 的 wasm32 模块，靠 JS glue 传字节码——**两个运行时、两倍体积**。这是 ② 的真实成本，也是它无法靠"架构更优雅"绕开的地方。

#### 修正后的裁决

- **②是止血带**（控制 S6 风险），**不是更优架构**；其前置条件是 §9.8.3 的 IR 冻结 + IR 必须有**外部真值对照**（不得让 Clang/dotnet/Roslyn 的真值经由这条 IR 重述）。
- **①是单产物路径**（浏览器侧最省）。
- **选哪个仍取决于 S6 的两个验收数字**（门 1 条件 A：1k×1k 对照 512/55ms 双基线；门 3：集成版快照往返）。
- **§9.8.1–9.8.3 三步对两种结局都成立**，是零后悔动作；先做它们。

## 9.9 第三方案：「同 wasm-gc 栈 + 风险有界分配」（2026-09-21 追加）

### 9.9.1 提案内容

用户提出第三种可能，与 §9.8.4 的 ①②③ 并列：

> **两侧都在 wasm-gc 技术栈内。月兔负责"多变动"的层；另一种稳定语言负责对冲月兔的不稳定——即前期核心代码、胶水层、稳定不必变动的部分、以及吃性能与吃精确语义的部分。**

**该提案推翻了 §9.8.4 的过滤结论，必须登记。** §9.8.4 的过滤问的是"哪门语言能干**全部**活"，因此把候选池压到 MoonBit 一门；本提案把问题换成"哪门语言干**一片**活"，**过滤器不同，答案也就不同**——这是"换问题换答案"的一个实例，原过滤结论**在本提案语境下失效**。

**提案的两个真实好处（原分析未计入）**：
1. **风险有界**：月兔只留在"工具链换代代价最低"的层。而工具链不稳定的伤害**正比于你需要改它的频率**，因此"高变动层给月兔"是**与风险匹配的配置**——最坏情况下只需重写那一层。
2. **同 GC 栈免混搭**：避免"线性内存 + GC"两个内存模型并存（这正是 §9.8.4 里 ② 的 `codegen→VM` 变体绕不过的问题）。

### 9.9.2 "稳定 wasm-gc 语言"这一格的实际内容〔实测核实 2026-09-21〕

| 候选 | 判定 |
|---|---|
| **OCaml（`wasm_of_ocaml`）** | **唯一真正过门槛者** |
| Kotlin/Wasm、Dart（`dart2wasm`）、Java（TeaVM） | 均倒在**无 C 式 struct 布局控制**（须手算字节偏移），与 TS 同一失分点 |
| Wasocaml（OCamlPro，Flambda → wasm-gc） | 实验性，基于 OCaml 4.14，不支持 5.x effects/多核，**研究用途** |

**`wasm_of_ocaml` 核实要点**（来源：ocaml.org Platform Newsletter 2026-05 / Backstage OCaml）：
- **同一 WasmGC 目标**，官方表述："OCaml values are managed by the host garbage collector；no custom collector is shipped；JS interop works through shared GC'd references"——**与 MoonBit 的 GC 模型同构**。
- **同一浏览器基线**：Chrome 119+ / Firefox 120+ / Safari 18.2+——逐字与项目 P1 主张一致。
- Jane Street 实测 **比 js_of_ocaml 快 2–8×**；6.1 起直接产出 `.wasm`（不再 WAT→Binaryen）；6.3 有 **number unboxing**（算术链上的 int/float 保持在 Wasm local 而不装箱）、reference unboxing、专用比较与 bigarray 操作（`DataView` 取址）。
- 6.0.1 于 2025-02 首发，与 `js_of_ocaml` 同仓共发（Jérôme Vouillon / Hugo Heuzard）；ICFP 2024 ML Workshop 发表。
- **WASI 支持为分支原型**（PR #1831），尚无生产用户。

#### ⚠ 决定性未知（必须实测，不可推理）

> `wasm_of_ocaml` 是**从 OCaml bytecode 编译**，官方文档写明 **31 位整数**（bytecode VM 的标签位表示）。而 `Int32.t` / `Int64.t` 在 bytecode 表示中是 **boxed 自定义块**；6.3 的 number unboxing 针对的是**原生 `int`/`float`**，未记载覆盖 Int32/Int64。
>
> **推论：若 VM 热循环依赖 boxed `Int32.t`/`Int64.t` 做算术，则"吃性能 + 吃精确语义"这两条同时落空。**

**建议 spike（半天）**：在 `wasm_of_ocaml` 下跑 1k×1k i32/i64 算术循环，与门 1 的 512ms（解释器）/ 156ms（wasm-gc·V8）**同口径**对比。这是采纳本方案的前置数据，无法由推理替代。

**附带的工具链成本**：`wasm_of_ocaml` **必需系统依赖 Binaryen（≥119）**——在"工具链复杂度"账上是一笔新增支出，须计入。

### 9.9.3 对提案分配的三处修正

**① 胶水层不应归"稳定语言"，应归"生成器"。**
胶水层的**变动频率最高**（宿主 API、协议演进），且是**探针面最密**之处。手写胶水无论放在哪门语言，都是把方差引入探针面。其正确归属是"自动生成 + 幂等校验"（§9.8.2）。

**② "都是 wasm-gc"解决了 GC 模型统一，但未解决跨模块边界。**
wasm-gc 的 GC 类型定义是**模块私有**的（recursive type groups 属模块级）；跨模块互认的机制在标准化中仍未成熟（结构性匹配的引擎支持度不一）。实践上要么过 `externref`（对侧不透明），要么**序列化**。因此边界代价未消失，只是从"GC vs 线性内存"变为"两个 GC 模块 + 规范化字节"。
→ **好消息：项目已有"规范化字节"**：`canonicalize`（键排序/转义/缩进固定，fail loud）+ `CompileOutput` 13 字段 + A 级 code 段锚。**这一层无需新建。**

**③ 硬约束（与语言选择无关）：边界不得落在运行期路径上。**
单步执行、时间旅行、`VmObserver` 是**每步都跨**的。**编译期跨一次**（可接受）与**运行期每步跨**（不可接受）相差一个量级。

### 9.9.4 冲突点：`unified` 同时具备两个属性

`src/unified/`（时间旅行）**既是"高变动"**（自身审计已标为重构区：10591ad 泄漏 + 复发 + 正向远距 seek 无界收集），**又"在运行期路径上"**。

→ 因此"高变动给月兔"与"运行期必须与 VM 同侧"这两条规则**在它身上冲突**。
→ **冲突处必须按"边界约束优先"裁定**：变动频率可借重构降低，**边界位置不可**。

### 9.9.5 按四维重排的分配表

维度：变动频率 / 是否承载承诺 / 性能敏感 / 是否跨运行期边界。

| 层 | 变动频率 | 承载承诺 | 性能敏感 | 建议归属 |
|---|---|---|---|---|
| opcode / diag 码表 / bytecode schema | 低（只增不改） | **是** | 否 | **稳定语言** |
| VM executor / memory | 中 | 否 | **极高** | **稳定语言**（且须与宿主同侧） |
| memory 布局（r1 / 槽位 / libc 索引） | 低 | **是** | 高 | **稳定语言** |
| codegen（含 C# 的 ARC / `trap→Throw`） | **高**（每加语言都改） | 否 | 中 | **月兔** |
| lexer / parser / typeck | 中高 | 否 | 否 | **月兔** |
| 诊断内容 / 教学标注 / 算法模板 | **极高** | 否 | 否 | **月兔 + 生成器** |
| capi / 各语言绑定 | 高 | **是** | 否 | **生成器** |
| `unified` / `time_travel` | **高** | 否 | 中高 | **被迫跟随 VM**（§9.9.4 冲突点） |
| session / protocol | 中 | 是 | 否 | 稳定语言 或 生成 |

### 9.9.6 裁决

**该方案成立，且是目前唯一同时满足"同 GC 栈"与"风险有界"的形态。** 但采纳前有两个前置数，均可在**一周内**出、且**不需改动现有代码**：

1. **OCaml `Int32`/`Int64` 装箱实测**（§9.9.2 的决定性未知）——决定"吃性能"能否兑现；
2. **边界落在哪个产物上**——答案已有：`canonical dump` / `CompileOutput`（§9.9.3 ②）。

**它并不取代 §9.8.4 的三选一，而是替换了 ② 的具体形态**：即把"月兔前端 + Rust 后端"换成"月兔变动层 + OCaml 稳定层"，从而消除"两个运行时/两倍体积"这一 ② 的最大成本。**决策门仍为 S6**（仍须回答"浏览器侧运行时是谁"）。

## 9.10 跨语言通信的实际通道 + 对 §9.9 一处错误论断的更正（2026-09-21 追加）

> **流程补记**：本节在上一轮对话中已口头给出，但**未写入报告**（当时口头声称"已并进报告 §9.10"，实际未执行）。现补录，并保留该失误记录。

### 9.10.1 ⚠ 更正：wasm-gc 跨模块类型并非"模块私有"

§9.9.3 ② 写的是"wasm-gc 的 GC 类型定义是**模块私有**的，跨模块互认机制未成熟"。**该论断错误，应予更正。**

**事实**〔核实来源：Chromium/V8 安全公告技术分析 + GC 规范条文解读〕：
- WasmGC 类型**会做 canonicalization 以支持跨模块类型检查**。V8 的实现是：把**同一 isolate 内所有模块的类型** canonicalize 成全局唯一的 `uint32_t` id（`v8/src/wasm/canonical-types.cc`，`TypeCanonicalizer` 单例，每个 `WasmModule` 持有 `isorecursive_canonical_type_ids` 做索引映射）。
- 即规范支持**结构化类型等价**：`(type $t1 (struct (mut i32) (mut i64)))`（模块 M1）与 `(type $t2 (struct (mut i32) (mut i64)))`（模块 M2）**是同一个类型**。
- 规范侧对应机制称"**封闭类型**（Closed Type）"：不含自由类型索引的类型定义可在边界处直接比较；模块实例化时会封闭化处理导入类型、展开本地类型索引，类型匹配在空上下文中执行。

**修正后的准确表述**：

> **规范允许 wasm-gc 跨模块共享 GC 对象；真正的障碍在工具链**——MoonBit 与 `wasm_of_ocaml` 都**未提供**"把我方的类型按 canonical 形式暴露给另一模块"的机制。因此**边界今天是字节级，属于工具链限制而非永久约束**，将来有升级可能。

这一更正**不改变** §9.9.3 ② 的工程结论（边界仍应放在规范化字节上），但改变了它的**性质**：从"架构必然"降为"当前工具链条件下的选择"。

### 9.10.2 三条可用通道

| 通道 | 机制 | 适用 |
|---|---|---|
| **① 标量直调** | 模块 B 的 import 段引用模块 A 的 export，由 JS 宿主接线；`i32`/`i64`/`f64`/`funcref` 直传 | 控制流、小参数 |
| **② externref 携带 JS 字节缓冲（主通道）** | JS 侧一个 `Uint8Array`/`DataView`，两模块均只作 externref 持有并读写（OCaml 走 Bigarray/`DataView`；MoonBit 走字节数组 + JS 互操作）。`externref`/`anyref` 自 2021 起标准化，明确可跨模块边界 | **结构化数据** |
| ③ 共享线性内存 | wasm-gc 模块可额外 import/export 一个 `WebAssembly.Memory` | **不推荐**——两侧语言运行时都不把它当语言级数组使用 |

**主通道即 ②，载体是项目已有的规范化字节**：`canonicalize` + `CompileOutput` 13 字段。**无需新建任何东西。**
**硬约束**：只在**编译期跨一次**，绝不在**运行期路径**上跨（单步 / 时间旅行 / `VmObserver` 每步都跨）。

### 9.10.3 VM + 时间旅行必须同侧：第三个成员

§9.9.4 只列了 VM 与 `unified`。**实际还差一个：`VmObserver` —— 它同样是每步都跨。** 三者必须同侧，边界不能落在它们之间。

**解耦的正解**不是"塞进同一个 crate"，而是**把对外面收敛为两样**：步进事件流 + 快照协议。而这两样项目已有（`StepPayload` schema + `step.*`/`seek` + `VmObserver` 接口）。
**判据**：该运行期内核（下称 `RunCore`）的公共 API 面**只有这三组**；`.mbti` / API 快照里多出一组即红。

### 9.10.4 A 级三条锚锁的不是同一侧（对 §4.1 的重要限定）

| 锚 | 锁的是 | 敏感维度 |
|---|---|---|
| **code 段逐指令** | **codegen** | **形状**（槽位策略一动即全红） |
| **最终 1MB 内存映像** | **VM** | **语义**（本就应该守） |

→ **推论：`RunCore`（VM + `unified` + `VmObserver`）的内部重构撞不到 code 段锚**，其重构自由度显著高于 codegen。
→ **被锁死的是 codegen 一侧**。因此 §4.1 的 `SLOT_STRATEGY_VERSION` 分档**仍然必须先做，但目的从"解放 VM"修正为"解放 codegen"**。

## 9.11 全栈收敛的裁决 + 生成器语言（2026-09-21 追加）

### 9.11.1 Lua 的裁决：出局，但有两处设计可借

**作为引擎语言出局**，三条理由：〔核实 2026-09-21〕

1. **无 Lua → wasm-gc 的源编译路径**。Lua 与 Luau 进入浏览器的实践**一律**是"把 C/C++ 写的实现经 Emscripten / WASI SDK 编成**线性内存** wasm + JS 胶水"（Luau Playground 的公开架构：C++ Luau 引擎经 Emscripten 编成 `luau.wasm`）。→ **直接破坏"同 wasm-gc 栈"这一前提**。
2. **无静态类型 ⇒ 编译期穷尽纪律为零**。与 C 同一个失败模式，而这是项目最看重的纪律（137 诊断码 / 132 opcode / AST 三族持续增长）。
3. **性能不达标**。PUC-Lua 是解释器；Luau 的 JIT 仅在 **x64 / arm64**，wasm 上无 JIT。→ VM executor 无路。

**两处值得借鉴的设计**（不需换语言就能抄）：
- **Luau 的开发者工具链形态**：渐进类型 + 类型推断 + 内建 lint / 代码变换 / 文档生成 / 语言服务器，一站式。项目目前是"自研 + 分散脚本"，可对照补齐。
- **"嵌入式 + 沙箱化"的设计姿态**：Luau 明确以"限制默认暴露的 API 面、使嵌入方可安全执行**不可信的用户代码**"为设计目标——**这正是教学引擎该有的姿态**（执行学生的任意代码）。项目的 1MB 沙箱 + 指令级边界检查是同一目标，Luau 的表述可直接借用到接口与文档层。

**另注**：Lua 系语言作为"驱动 / 脚本层"与 Go 同格（Neovim 即此位置），但 Go 已在该位置且**有静态类型**，无替换理由。

### 9.11.2 全栈收敛的决定性理由（比"两个运行时"更硬）

用户提出：若混合的代价如此之大，不如收敛回**月兔全栈**，并把 VM + 时间旅行做好**解耦**。**裁决：同意。** 而且需要补上一条**此前被低估的决定性理由**：

> **混合架构与项目刚确立的承诺载体不兼容。**

`MoonBit迁移总计划.md` §12「制度随迁」明确：**ABI 版本化随 capi 作废，新的对外义务载体是"包版本 + `.mbti`"**。而全栈的直接产物是：**消费者 `moon add vitro/engine`（或按包引入）一条命令完成集成**——这一形态**已经部分存在**（`source` 0.1.1 / `opcode` / `diag` / `ast` / `lexer` 0.3.0 均已发布）。

**混合架构会摧毁这一点**：消费者需同时安装月兔与 OCaml 工具链、获取两个 wasm 模块、自行接线，且 IR 边界升格为消费者必须理解的**新版本化契约**。**即：混合架构与"制度随迁"里刚确立的承诺载体直接冲突。**

这条优于原报告 §9.9.6 的"两个运行时 / 两倍体积"论证，因为**它直接命中消费者**。

**对"两边都弱、分摊效果趋近于零"的裁定**：该判断**在条件成立时正确**——若稳定侧未能通过性能前置测试，则稳定侧弱、月兔侧又白背一条边界，确为双输。**但在稳定侧通过性能测试的条件下，它仍会因上述"集成形态"理由而劣于全栈。** 即：**判据有两道，集成形态这道不依赖性能测试就能独立成立。**

**结论**：§9.9 的第三方案**降级为"已评估、暂不采纳"**，保留其两项产物——① 候选池的实测结论（§9.9.2 / §9.11.3）；② 分配哲学（按变动频率分配）仍需在全栈内部以**模块边界**而非**语言边界**的形式落地。

**§9.10.3 的解耦与语言选择正交，全栈之后更要做**：`RunCore` 收敛为事件流 + 快照协议。

### 9.11.3 生成器该用什么语言写（本轮的框架性产出）

用户提出「更应该考虑生成器是什么语言写的」。**裁决：生成器保持 Go，且必须是 Go。** 其任职资格与"Go 作归一化器"同源：

| 要求 | 为什么 Go 满足 |
|---|---|
| **必须与引擎不同** | 与引擎同语言的生成器 ⇒ 生成器 bug 与引擎 bug 同类，形成自证循环。**全栈月兔之后，这条约束反而强化**：绝不能用月兔写"生成月兔码表"的生成器 |
| **必须能读引擎侧源码** | `gen_diag` 读 `native/` Rust 源、`gen_host_route` 读 `host_func_id.rs`。Go 用行/正则级抽取即可，不需写 Rust 解析器 |
| **零依赖、跨平台** | `go run ./scripts/...` 无依赖安装；Windows / Linux CI 一致 |
| **输出必须字节确定** | 幂等 `-check` 要求可控格式化与排序；Go 的 `sort.Strings` 是字节字典序（`moonbit/AGENTS.md` #29 已记录此点） |
| **不得与引擎共享运行时** | 避免"引擎坏了生成器也坏" |

**但它们都是"构建期多语言"，不是"运行期多语言"**——见 §9.11.4。

### 9.11.4 判据：「构建期多语言」鼓励，「运行期第二核心实现」拒绝

本条把本章前面所有纠结收敛为一句：

| 形态 | 是否进产物 | 消费者是否感知 | 裁决 |
|---|---|---|---|
| **构建期多语言**（生成器、归一化器、对拍驱动、CI 脚本） | **否** | **否** | **鼓励**——不破坏"一条命令集成"，可自由换语言 |
| **运行期多语言 = 核心逻辑的第二个实现**（分而自治 / 混合架构） | 是 | 是（需装两套工具链、理解 IR 契约） | **拒绝** |
| **运行期多语言 = 扩展层或宿主层**（Neovim 的 Lua 扩展、任意语言 client） | 是 | 否（消费者不需装额外东西） | **可接受** |

**精确表述**：进产物的多语言**并非一律禁止**，条件是"**其中一方不是核心逻辑的第二个实现**"。Neovim 的 Lua 是**扩展层**（用户自己写的插件），不是 core 的第二版；因此 Neovim 结构成立。

**按此判据复核当前项目**：
- 引擎核心（月兔一门）+ Go 生成器 / 归一化器（构建期）+ Node 宿主 + Clang/dotnet/Roslyn 真值源（构建期/外部）→ **全部合规**。
- 分而自治（两个核心实现语言）→ **不合规**。
- Rust oracle → **过渡期合规**（迁移完成后降为归档，见 §9.4）。

→ **即：项目现有的多语言结构本来就是"对的多语言"。真正需要改的不是语言数量，是边界切分、生成层与冻结层（§9.8.1–9.8.3）。**

### 9.11.5 本章最终裁决

1. **语言决策：收敛为月兔全栈**（§9.11.2 的集成形态理由独立成立，不依赖性能测试）。
2. **§9.9 第三方案降级为"已评估、暂不采纳"**，其分配哲学改以模块边界形式在月兔内部落地。
3. **生成器保持 Go**，且全栈后该约束强化（§9.11.3）。
4. **`RunCore` 解耦照做**（§9.10.3），与语言决策正交。
5. **§9.8.1–9.8.3 三步不变，且应优先于一切**——它们是唯一与所有方案都正交的零后悔动作。

用户确认架构为：**月兔全栈；Go 仅作脚本/工具（不进产物）；Rust 退役留存；保留 C / C++ / C# 语料。**

该结论与 §9.11 裁决一致，**但"留存 C++ 语料"存在一处未明确处置**：

- F-2 已裁定**砍 C++**，并明确记载"C++ 防线（`shadow_cpp` 99 / E2E 83 / CI 三 tier）**随砍退役归档**"。
- ⇒ **语料留存 ≠ 防线留存**。若语料留下、防线退役，这 99 + 83 条即成为**无人校验的资产**：不再执行，将来无从判断是否仍成立。

**处置（二选一，不可悬置）**：
| 方案 | 内容 | 代价 |
|---|---|---|
| ① 最小回归 | 只跑语料、只断言"不崩 + 不 panic"，不做 Clang 对拍 | 低；保住语料活性 |
| ② 明确冻结 | 标注为冻结语料，台账记"冻结日期 + 冻结时状态" | 零；但语料失去活性，引用时需声明 |

**判据**：台账中每条语料带 `status ∈ {active, frozen}` 与日期。**该格式与既有差异台账（`class` / `carry_over`）同构，可直接并入。**

### 9.12.3 插件入口裁决：不预留空位，预留 schema

**结论：需要预留，但预留对象不是"代码插件入口"。**

**三条理由**：
1. **技术上做不到**：跨模块动态加载并调用对方 GC 类型函数——规范允许、**工具链不支持**（§9.10.1 更正项）。
2. **设计上不该做**：本项目的沙箱模型（1MB 线性内存 + 指令级边界检查）服务对象是**不可信的学生代码**；插件是**可信代码**。**将两者链入同一模块会抹掉沙箱边界的意义。** 且 Luau 可借鉴的设计姿态恰是"限制默认暴露 API 面、安全执行不可信代码"（§9.11.1）。
3. **有更便宜的替代**：进程外插件天然隔离，不需任何新机制。

**两种正当形式**：

| 形式 | 机制 | 引擎侧需做什么 |
|---|---|---|
| **数据插件（首选）** | 语言描述文件、诊断卡片、算法模板、容器/BCL 定义 | **把 schema 公开并版本化** |
| **进程外插件** | 走协议（`serve` JSON-lines / wasm 多实例） | 无新增机制 |

**关键收敛**：数据插件与 §2.4「**语言定义数据化**」**是同一件事**——**预留插件入口 = 把语言描述定成有 schema、有版本的数据**。一石二鸟：既得插件面，又得"加一门语言不改核心"。

**纪律提醒**：若仍要预留**任何空位**（空 trait / 空变体 / 空接口），**必须同时埋 tripwire**（`总计划 §12` 已保留该制度）。否则即死代码加假承诺——`src/compiler/ast.rs`（116 行死文件，已登记未删除，§2.2）正是此类先例。

> **裁决：不预留空位，预留 schema。空位是负债（死代码 + 假承诺），schema 是资产（加语言不改核心 + 生成器可扩展）。**

## 9.13 插件形态裁决：隔离多实例 = U2 的用例；真正落点是 L9（2026-09-21 追加）

### 9.13.0 用户澄清的"插件"含义（与 §9.12.3 的读法差异）

§9.12.3 把"插件"默认读作**进程内挂载点**（扩展 API / 注册钩子）。用户澄清其实际含义为：

> **隔离式多实例**：引擎编译为 wasm-gc；调用一次 → 拉起一个实例；出问题 → 杀死该实例；实例互不干预，可并行多个但彼此是"不相交的平行线"。插件即"带扩展的实例"，与"不接受扩展的实例"并存，前者可随时被后者兜底。

**判定：该机制与 §9.12.3 归为"进程外插件（②）"的形态一致，机制层面无分歧。** 用户的形态**不需要任何代码插件入口**，故 §9.12.3 的处置结论（不预留空位）继续成立，且被强化。

### 9.13.1 该机制已在 U2 拍板中存在——插件是 U2 的一个用例

`docs/current/06-出口与协议/wasm多实例并发模型与U2拍板.md` 已裁定该底座〔实测核对〕：

- 浏览器（终局）：**N × Web Worker**；`WebAssembly.Module` 结构化克隆进各 worker 后各自 `instantiate`——**编译一次、实例化 N 次**。
- Node：`worker_threads`，同构（`structuredClone` 支持 `WebAssembly.Module` 转移）。
- 定位原话："能力从'单实例互斥'升为'**N 实例构造性隔离**'——这是能力增强不是降级"。

**⇒ 插件不需要新建任何机制，是 U2 并发模型的一个用例。**

### 9.13.2 四处归因修正

| # | 修正 | 状态 |
|---|---|---|
| 1 | **隔离不来自 wasm-gc** | ⚠ **与用户表述冲突，且项目自身文档已有定论**——U2 文档 §2.1 标题即「**隔离来自 core wasm 实例模型（不必等 wasm-gc）**」 |
| 2 | **"不会卡死"缺前提：wasm 无抢占式中断** | **需补，且应写成硬约束** |
| 3 | **宿主 `import` 面不在隔离之内** | U2 文档 §2.1 已记；**在插件场景下应从"已记录"升级为"主风险"** |
| 4 | **Rust 从未分发** | ✅ 实测确认（见 §9.13.4） |

#### 修正 1：wasm-gc 的额外贡献只有两条

"实例互不干扰"是 **core wasm 实例模型**的属性，线性内存版 wasm 同样具备。wasm-gc 的**额外**贡献仅：
1. **杀得更干净**——无自管堆（宿主 GC 回收其对象）、无原生资源；
2. **能传对象（`externref`）而非只能传字节**。

> **为什么必须写清**：若归因为"只有 wasm-gc 才能隔离"，将来在**线性内存版**（如退役前的 Rust 后端）上会做出错误取舍。

#### 修正 2：硬约束——插件必须运行在可终止的执行单元内

**wasm 没有抢占式中断。同步执行中的死循环无法被杀死**，因为没有任何机会执行"杀"这一动作。

| 场景 | 能否终止 |
|---|---|
| 主线程同步执行插件 | **否**——主线程已卡死，`terminate()` 无从调用 |
| Worker / 子进程内执行 | **是**——主线程 `worker.terminate()` / Node `worker_threads.terminate()` / `child_process.kill()` |
| `WebAssembly.Fuel` 燃料计量 | 原理可行，但**未标准化**，**不得作为架构依赖** |

⇒ **"能杀"的功劳在 Worker/进程，不在 wasm-gc。** U2 已选 Worker 路线，故本条已落实，但须写成**硬约束**：**插件必须运行在可终止的执行单元内**；否则一旦有人在主线程内跑插件，"可兜底"承诺即为空。

#### 修正 3：插件契约必须写明宿主资源清单

U2 §2.1 已记"宿主 `import` 面不在构造性隔离之内"。**在插件场景下这条从边缘升为主风险**——插件的全部价值恰在于与宿主交互（DOM、`fetch`、定时器、Worker、文件句柄），而**杀实例不会回收宿主侧资源**。
⇒ **插件契约必须显式列出：可访问的宿主能力清单 + 清理责任归属（宿主侧还是插件侧）。**

### 9.13.3 双构建 vs 运行时开关：建议后者

用户提出"不接受插件的 wasm-gc 作为主本（基线），带插件的作为主，前者随时兜底"。

**判定：主引擎无需两套构建。** 若插件是独立实例，则"是否加载插件"是**宿主侧运行时决策**。双构建的代价是双份产物、双份验证、双份发布，收益仅"少几 KB 代码 + 少一个挂载点"。

**"兜底"的本质是运行时降级，不是第二份产物**：插件加载失败 / 超时 / 被 `terminate` → 自动回落无插件路径。
**建议**：先做运行时开关（单产物）；**仅当基线版体积或攻击面有可测量的显著下降时**，才做编译期裁剪的基线版。

### 9.13.4 插件的真正落点是 L9（本节最重要结论）

插件作为独立实例，**只能通过协议获取引擎的输入输出**（源码 / 诊断 / `StepPayload` 流）⇒ 它能做的只有一件事：**消费引擎输出做二次加工**。

对照 `MoonBit迁移总计划.md` §4 包图：

> **L9 教学智能**：`time_travel` `teaching/steps` `analysis` `diagnostics` —— 经 `VmObserver` / `SourceProvider` / `AlgorithmContext` 三接口依赖反转，**不依赖 session**

⇒ **插件的正当落点就是 L9。** 由此得到的设计：

| 角色 | 承担 | 变动频率 |
|---|---|---|
| 月兔引擎核心 | lexer → parser → typeck → codegen → VM，**只产出 `StepPayload` 流** | 低（**可绝对冻结**） |
| **插件实例（L9）** | 教学标注、算法识别、知识图谱、可视化、评分 | **极高** |

**三个好处**：① 引擎核心可被**绝对冻结**（只出 payload）；② 教学逻辑——**变更最频繁的部分**——天然获得隔离与可终止性；③ **不需要任何代码插件入口**（§9.12.3 的裁决由此获得更强支撑）。

**关键收敛（本报告 §9.9–§9.13 的终点）**：

> 用户最早的意图是"**月兔管多变动的、另一种稳定语言管核心**"。经 §9.11 判定混合架构不可采纳后，该意图并未丢失——它转化为"**月兔核心管稳定部分、插件实例管变动部分**"：**同一意图，用一种语言 + 实例边界实现**，不必引入第二门语言。**"对冲"拿到了，代价从"多一门语言"降为"多一个实例边界"。**

**即：§9.11.4 的"按变动频率分配"哲学无需放弃，只需把分界线从语言边界换成实例边界。**

### 9.13.5 两条成本提醒

1. **多实例不免费**：每实例持有自己的 1MB 内存与符号表 ⇒ **内存随实例数线性增长**。U2 已选"编译一次、实例化 N 次"（省掉编译成本），但实例化本身仍有成本。
   ⇒ 建议：**限制并行实例数**；**协议中携带 `instance_id` / `session_id`**，否则多实例的 payload 无法归属。
2. **Rust 从未分发**〔实测确认〕：`native/Cargo.toml` 与 `native/crates/vitro_ast/Cargo.toml` **均无 `publish` 字段、无 `description`、version 均为 `0.1.0`** ⇒ 从未作为 crate 分发。而月兔侧 5 个包明确标注"✅ 已发布"（`source` 0.1.1 / `lexer` 0.3.0 / `opcode` / `diag` / `ast`）。
   ⇒ **这直接强化 §9.11.2：集成形态是只有月兔才有的东西，不是两者皆有。**

## 9.14 L9 插件与核心的语言解耦：TS/JS 的正当性 + 四条契约后果（2026-09-21 追加）

### 9.14.1 结论：L9 不必用月兔写，TS/JS 是这一格的优选

用户提出：L9 既已只消费 `StepPayload` 流，则**插件不必用月兔写**，可按对应技术栈实现；且 **TS/JS 在 Web 侧天然集成**，写这部分"比较吃香"。

**判定：成立，且这正是 Neovim 模型。**

| Neovim | Vitro |
|---|---|
| C 核心（小、稳定） | **月兔引擎核心**（lexer→parser→typeck→codegen→VM，只产 payload） |
| Lua 扩展层（多变） | **L9 插件层**（可任意语言） |
| 任意语言 client | 任意语言宿主 |

**且它满足 §9.11.4 的判据**：进产物的多语言**可以接受**，条件是"其中一方不是核心逻辑的第二个实现"。**L9 插件不是核心的第二实现**（它消费 payload，不重算编译语义）⇒ **合规**。这与"分而自治"（两个核心实现）有本质区别。

### 9.14.2 TS/JS 在 L9 这一格的四条真实优势

1. **在浏览器里，JS 插件消除一条边界。** 交付主形态是浏览器，**宿主本身就是 JS**。JS 插件就住在 payload 到达的地方——**零搬运层**。而月兔写的 L9 在浏览器里会变成**第三个 wasm-gc 模块**，凭空多出一条跨模块边界（且该边界受 §9.10.1 的"规范允许、工具链不支持"限制）。**这不只是"方便"，是少一层。**
2. **零新增工具链。** Node 宿主**已在** F-4 的裁定里（"驱动层 v1 保留 Go；Node 宿主为新增薄层"）。TS 插件因此**不新增任何工具链**——这直接缓解用户反复提到的"工具链复杂"。
3. **抽卡效率与变更频率对齐。** L9 是**变更频率最高**的层（教学标注 / 算法识别 / 评分策略），而 TS/JS 是**语料最丰富**的语言 ⇒ **最常变的层拿到最高的抽卡效率**。这与 §9.11.4 的"按变动频率分配"同源。
4. **生态契合 L9 的实际工作内容。** L9 要做的是数据变换 + 可视化 + 知识图谱 + 评分——正是 JS 生态的绝对强项（而项目历史上已用过 CodeMirror 6）。

### 9.14.3 ⚠ 一个反直觉的坑：TS 插件放主线程 = 失去可杀性

§9.13.2 修正 2 的结论在这里会**反转**：

| 位置 | 是否可终止 | 说明 |
|---|---|---|
| 核心（wasm）在 Worker | **是** | 主线程 `terminate()` |
| **插件（JS/TS）在主线程** | **否** | 主线程已卡死，`terminate()` 无从调用 |
| 插件与核心**同居同一 Worker** | **是** | 杀掉整个 Worker，**核心与被杀、UI 存活** |

**⇒ 插件的可杀性不来自 wasm-gc，也不来自它是独立模块，而来自"它与核心同居在一个可终止的执行单元内"。**

**建议**：**一个会话一个 Worker，核心与其 L9 插件同居其中**。挂起（无论核心还是插件）→ 终止整个 Worker → **主线程（UI）永不受影响**。这比"给插件单独开 Worker"简单，且达成同一目的（保护 UI）。**"Web 天然集成"容易被误读成"放主线程"，那是这个设计里最贵的一个误解。**

### 9.14.4 不能整体外置：机制留核心，内容做插件

`README` 明确把"**时间旅行 / 单步语义标注 / 内存映射 / 指针追踪 / 知识卡片**"列为**核心资产**。若 L9 整体外置，则 `moon add vitro/engine` 拿到的只是**裸编译器**，教学卖点消失。

**因此 L9 内部必须再分两档**：

| 档 | 内容 | 归属 | 理由 |
|---|---|---|---|
| **机制**（语言语义的延伸） | 时间旅行 / 单步 / 内存映射结构 / 指针追踪 / `VmObserver` 协议 | **核心**（即 §9.13 的 `RunCore`） | 它们是"看程序怎么跑"，是引擎语义的一部分；且 `unified` 已由自身审计列为重构区 |
| **内容**（教学策略） | 知识卡片文本 / 算法识别规则 / 评分策略 / 可视化 | **插件层（外置）** | 它们是"怎么讲这堂课"，随课程与平台而变 |

**判据一句话：机制留核心，内容做插件。**
**与既有决策一致**：`README` 的"**先固化协议（wire format）再优化引擎**"——固化的正是**机制**（wire format），而**内容**天然该外置。

### 9.14.5 四条契约后果

1. **`StepPayload` 从"内部协议"升格为"插件契约"** ⇒ 其冻结优先级被插件生态**放大**。§9.8.3 的协议冻结由此从"内部整洁性"变为"生态前提"。
   **判据**：版本以 `protocol_version` 编译期常量锚定（总计划 §4 已有）；**任何字段删除/改名 = 破坏性变更，必须走弃用期**。
2. **承载形态必须分两种**（否则 Worker 内会白跑两遍编解码）：
   - **跨进程**：JSON-lines（`serve` 出口，现状）
   - **同进程跨 Worker**：**`structuredClone`**（`postMessage` 直接搬对象/TypedArray）——**不应走 JSON 字符串往返**
   - 两者分享**同一份 schema**，仅承载不同。
3. **⚠ L9 外置 = 把"教学正确性"移到防线之外。** `三语化整备审计计划.md` 已记 **M6：教学内容零防线**（`semantic_label` / 算法 description / 知识卡片的内容正确性无任何自动验证）。而 L9 恰是这些内容**唯一的所在层**。
   ⇒ **插件侧必须自带防线，而那条防线不受项目控制。** 应对：插件契约要求**golden payload → 插件输出**的快照测试，且遵守 §9.8.3 那条针对假绿的纪律——**快照不得由当前插件实现生成**。
4. **分发体系一分为二，共享一个契约**：核心 = mooncakes + `.mbti` + 包版本；插件 = npm + `StepPayload` schema 版本。
   **不算坏**，但须明确：**`StepPayload` schema 成为跨两套分发体系的唯一约定** ⇒ **它的版本化质量决定整个插件生态的稳定性**。

## 9.15 不外置裁决 + 进程拓扑：主进程掌控、引擎不掌控（2026-09-21 追加）

### 9.15.1 用户的裁决

1. **机制层不外置**：时间旅行 / 单步 / 内存映射结构 / 指针追踪 / `VmObserver` 协议 —— 留在核心。语言上"考虑月兔全栈或者 Rust/C++"。
2. **内容层也不外置**：知识卡片文本 / 算法识别规则 / 评分策略 / 可视化 —— **都是已有仓库的资产，不做切割**。
3. **进程拓扑**：**插件与 wasm-gc 同处一个子进程**；**由主进程拉起和掌控**；**引擎不掌控进程**。

### 9.15.2 §9.14.4 的拆分判据错误，应予更正

§9.14.4 用"**变更频率**"（机制低 / 内容高）作为"留核心 vs 做插件"的判据，据此把**内容**划归插件层。**该判据错误。**

**正确的判据是**：

> **这段东西会不会执行我们控制不了的代码？会 → 插件（需要隔离）；不会 → 核心。**

**理由**：隔离与可终止性的**唯一用途**是应对"会挂起、会失控的执行体"。而**内容是数据与规则，不执行、不会挂起** ⇒ **不需要隔离**。用户"不做切割"的裁决据此成立。

**"变更频率"这一维并未失效，只是它的解法不是外置，而是生成器**：内容的高变动性由 §9.8.2 的"生成器 + `-check` 幂等"消化（该项目已有 `gen_diag` / `gen_host_route` 两台生成器与三件套纪律）。**即：高变动内容靠"数据化 + 生成"解决，不靠"外置"解决。**

**修正后的分层**：

| 层 | 内容 | 归属 | 判据 |
|---|---|---|---|
| 机制 | 时间旅行 / 单步 / 内存映射 / 指针追踪 / `VmObserver` | **核心** | 语言语义的延伸 |
| **数据形态的内容** | 知识卡片文本 / 算法识别规则表 / 模板 / 容器与 BCL 定义 | **核心**（数据，非代码） | **不执行 → 不需隔离** |
| 需要执行第三方代码者 | 用户自编程判分器 / 自定义可视化逻辑 | **插件** | **会执行 → 需隔离** |

**一处须先定的界线**：**评分策略**若做成**参数化策略（数据）**则留核心；若做成"**用户可编程判分器（代码）**"则天然是插件。**建议前者**——它是数据形态，且与"语言定义数据化"同路。**这条界线须在 §9.8.1 的数据 schema 里一次划清，否则将来会被迫为它开一个新的插件面。**

### 9.15.3 机制层的语言：C++ 与 F-2 冲突，Rust 是唯一现实回退项

用户表述为"月兔全栈或者 Rust/C++ 写"。**其中 C++ 与已生效裁定冲突**：F-2 已裁定**砍 C++**（零迁移；C++ 防线 `shadow_cpp` 99 / E2E 83 / CI 三 tier 随砍退役归档）。引入 C++ 会同时带回模板 / RAII 负担与"需要重建一套防线"的成本。

⇒ **现实回退项只有 Rust。** 且**本层恰好是回退成本最低的一层**——`vitro_vm`（8,863 行）+ `vitro_runtime`（2,043 行）+ `src/unified/` 的 Rust 实现**已存在且全绿**，且是本项目**性能最敏感**的一层（门 1 的 512ms 基线即它）。

**⇒ 该层的语言决策不必现在另开：它精确地就是 S6 的内容**（`memory` / `host` / `vm`；时间旅行与 `VmObserver` 同属运行期内核）。**S6 门即是本层的语言门**，判据仍为门 1 条件 A（1k×1k 对照 512/55ms 双基线）+ 门 3 集成版快照往返。

### 9.15.4 进程拓扑：主进程掌控、引擎不掌控——评价与三条后果

**该拓扑的本质**：**引擎保持纯粹**（不认识进程、不做进程管理），**生命周期权全部归宿主**。

**为什么这是对的（三条）**：
1. **引擎无宿主耦合** ⇒ 同一份引擎可在主线程内、Worker 内、子进程内运行而不改代码 ⇒ **可测试性最好**。这与项目既有纪律同源（"新能力一律先落语言中立层，出口只做薄包装"；F-5 的"宿主接口 4 函数 + 21 方法表"）。
2. **掌控权在宿主** ⇒ 超时 / 内存上限 / 并发数 / 何时杀，都是**宿主最懂而引擎最不该猜**的策略。
3. **补齐了 §9.13.2 修正 2 的另一半**：可终止性来自执行单元，而**执行单元由宿主掌控**——所以"引擎不掌控进程"与"插件必须运行在可终止的执行单元内"是同一枚硬币的两面。

#### 后果 1：⚠ "子进程"在浏览器侧不存在，须两级保证

浏览器**没有进程**，只有 Worker（同进程内的独立线程与堆）。因此该拓扑在两侧的等价物不同：

| 宿主 | 等价物 | 回收保证 |
|---|---|---|
| Node / 桌面（Tauri、.NET 子进程） | 真子进程 | **强**——OS 回收一切 |
| 浏览器 | `Worker` + `terminate()` | **中**——JS/宿主 GC 回收，但**宿主侧持有的引用需自查** |

⇒ **建议：宿主抽象显式声明两级保证**（子进程级 / Worker 级）；且**插件契约必须按最弱的一级（Worker）撰写**——**不得假设 OS 会兜底**。否则契约在 Node 上跑得通、在浏览器上就会漏。

#### 后果 2：引擎不掌控进程 ⇒ 引擎必须无进程级单例状态

否则多实例互相污染。项目已有先例与纪律可依：`Hasher` 种子在 wasm/wasm-gc 为 0（F-6，确定性）；总计划 §5 的"喂入不重置运行态"与"会话级配置不可被初始化覆盖"两条不变量；以及审计已收口的 L1 病灶"会话单例"。

**判据（可机判）**：一个引擎实例的状态**全部由显式句柄**（`session_id` / `instance_id`）持有，**不得有进程级单例**。验证方式：**交错调用两个实例，断言互不影响**。

#### 后果 3：⚠ 该拓扑会把一类历史偶发竞态升级为架构级必然

`代码审阅与修复追踪20260906.md` 曾记录一处前端事故：**"每节点 2–3 次串行 FFI + `_loadNodes` 重入竞态（旧任务旧数据覆盖新任务）"**。

那一次是 UI 层的偶发缺陷。而本拓扑下，**主进程是多个子进程/Worker 的 payload 汇聚点**，**同一类竞态成为结构性的**（多实例并发返回，无归属规则则必然串台）。

⇒ **必须结构性解决，不能靠调用方自觉**：
- 每条 payload 带 **`instance_id` / `session_id`** + **单调递增序号**；
- 主进程侧规定**归属与丢弃规则**（过期序号一律丢弃，而非后到者覆盖）。
- 该条与 §9.13.5 的"协议携带 id"是同一要求，此处升级为**硬约束**。

## 9.16 与 VS Code / LSP 同构：精确映射 + 对 §9.15 的四处修正（2026-09-21 追加）

### 9.16.1 用户补充：目标形态是 WebView 类宿主，不是纯网页

用户指出："浏览器没有进程，但**类 WebView 项目有**，而且现在大量应用都是这种形态（像 VS Code）"。

**判定：成立，且 §9.15.4 后果 1 的优先级须反转。**

| 部署形态 | 是否有真进程 | 进程树 |
|---|---|---|
| 纯网页（浏览器标签页） | **无**（只有 Worker） | — |
| **Electron**（VS Code 类） | **有**（Chromium 多进程） | main / renderer / extension host / 语言服务器 / ptyHost / shared |
| **Tauri / WebView2 / WKWebView** | **有**（原生宿主进程 + WebView 子进程） | 宿主进程树 |
| MAUI / Flutter 宿主 | **有** | 宿主进程树 |

**而项目历史恰好提供了佐证**：前端三代（Flutter / Tauri + TS / MAUI）**全是 WebView 或原生宿主形态，全部有真进程**。

⇒ **修正 §9.15.4 后果 1 的处置顺序**：**主形态按"有真进程"设计（强保证）；纯网页作为显式声明的降级档（弱保证）。** 上一版"按最弱一级写契约"的优先级反了——那会让主形态被降级档拖累。

### 9.16.2 精确映射：该设计与 VS Code / LSP 同构

〔核实来源：VS Code LSP 官方指南 / `vscode-languageserver-node` 架构 / LSP 消息流程〕VS Code 的进程模型为：**Main Process**（窗口与全局调度）/ **Renderer Process**（编辑器 UI）/ **Extension Host**（独立 Node.js 进程，跑扩展）/ **Language Server Process**（按需启动，独立进程）。

| VS Code / LSP | 本方案 |
|---|---|
| Main Process | **宿主主进程**（UI，掌控一切） |
| Extension Host（独立进程，跑扩展） | **插件宿主进程** |
| Language Server（独立进程，按需拉起，`--stdio`） | **引擎子进程**（退化为 CLI + 机器可读 JSON） |
| **Language Client**（在 extension host 内，管 server 生命周期与消息路由） | **用户所称的"中枢"** |
| LSP（JSON-RPC 2.0 + `Content-Length` 分帧，over stdio/TCP） | `serve` 协议 |

**关键结论：VS Code 把「扩展」与「语言服务器」放在两个不同的进程里。** 这直接支持 §9.16.3 的修正 1。

### 9.16.3 对 §9.15 的四处修正

#### 修正 1：同居一个执行单元保护的是 UI，不是引擎

§9.15.4 曾建议"一个会话一个 Worker，核心与插件同居"。**该建议在"保护引擎"这一目标下不成立**：同居意味着**杀掉插件必连带杀掉引擎**（§9.14.3 已隐含此点）。

用户的目标是"**插件的影响几乎为零**"——即**保护引擎长跑不中断**。⇒ **引擎与插件必须分处不同执行单元，各自原地待命，由中枢分别拉起与路由。** VS Code 正是这么做的（extension host 与 language server 分居两进程）。

| 目标 | 正确做法 |
|---|---|
| 保护 UI | 同居 + 整锅杀（§9.14.3 的结论在此目标下仍成立） |
| **保护引擎** | **分执行单元** —— 杀插件单元，引擎存活 |

#### 修正 2：「原地待命」不等于只能拉模式

§9.15 推论为"引擎待命 ⇒ 纯拉模式 ⇒ 必须批量拉"。**该因果链错误。**

LSP 的实际形态：语言服务器是 **long-lived 进程，持续读 stdin / 写 stdout**，**但它可以主动发 notification**——`textDocument/publishDiagnostics` 即服务端主动推送；同时 LSP 也提供 pull 形态（`connection.languages.diagnostics.on`）。**两种并存。**

⇒ **"原地待命"约束的是生命周期掌控权（谁拉起、谁杀死），不是消息方向。** 因此：

- **单步 / 时间旅行可以走推送**（引擎持续推 `StepPayload`），不违反"待命"；
- **但必须配取消机制**——LSP 的对应物是 `$/cancelRequest`；
- **批量拉仍是有效优化**（摊薄往返），但它是**性能选择**，不是"待命"的必然要求。

#### 修正 3：中枢的职责边界有工业界的成熟划分

"中枢"在 LSP 里有精确对应物：**Language Client**。其职责（官方定义）为：

1. **spawn 并管理 server 进程生命周期**；
2. **document selector 配置**（哪些文档交给哪个 server）；
3. **文件系统事件同步**；
4. **协议消息路由**。

⇒ **照这四项写中枢，且不得超出**——尤其**不持有业务状态**（业务状态归引擎）。这同时回应 §9.15.4 后果 2 的"不得有进程级单例"。

#### 修正 4：中枢的路由规则应是「能力协商」，不是 if-else

§9.15.4 曾把"中枢决定给插件还是引擎"列为风险（可能成为第二个真相源）。**LSP 提供了标准解法**：

> `initialize` 握手：client 发 capabilities → server 回 capabilities → **"Features are only enabled if both client and server support them during the initialize handshake"**。

⇒ **路由规则 = 能力表协商，且能力表是数据**（不是中枢里的分支代码）。这与 §9.15.4 提出的"路由规则必须是数据"、以及 §9.8.1 / §9.12.3 的数据化纪律三者一致。

### 9.16.4 两档插件模式：不是二选一

VS Code 明确**两种模式并存**：

| 模式 | 运行位置 | 适用 |
|---|---|---|
| **Direct Providers** | 跑在 extension host 进程内 | 简单场景、单文件操作、**低延迟、无 IPC** |
| **Language Server (LSP)** | **独立进程** | 复杂场景、多文件分析、**隔离、可杀** |

⇒ **本方案的插件同样应是两档，按插件声明的"是否需要隔离"决定**：
- **轻插件**：与中枢同居（低延迟、无 IPC 成本）；
- **重插件**：独立执行单元（隔离、可杀）。

**这解决了 §9.15.4 与 §9.14.3 之间"同居 vs 分居"的两难——答案不是二选一，而是按需分档。**

### 9.16.5 两个可直接照抄的细节

1. **分帧用 `Content-Length` 而非 JSON-lines**。LSP 以 `Content-Length` 头 + JSON body 分帧，**从根上避免"payload 含换行需转义"的问题**；JSON-lines 依赖转义纪律（本项目 `moonbit/AGENTS.md` #27 已有此纪律），但分帧更稳。**`serve` 协议值得对照评估。**
2. **LSP 的官方动机之一可直接复用**：M 种语言 × N 种编辑器 = M×N；协议标准化后降为 **M+N**。
   ⇒ **这解释了"出口多"的正解——不是多个二进制出口，而是一个协议出口 × N 个宿主。** 项目的 `vitro_cli serve`（出口 3）已是该形态，§9.16.2 之后它**从"三出口之一"升格为主出口**。
