# 05 · 踩坑清单（症状 → 根因 → 修法）

按"会静默产生假结果"的严重度排序。**前五条都会让你拿到看起来合理、其实全错的结论。**

## P1 · 判据全变 `JUDGE_ERROR(no-ok-field)`，而手工跑却正常

- **症状**：计划任务里所有 vitro 判据 `no-ok-field`，clang/gcc 正常；**手工在 Bash 里跑同一个文件却拿到完整帧**。
- **根因**：`subprocess.run(..., text=True)`。计划任务环境里它把 stdout **读成空串**。
- **证据**：同一目录两次探针 —— `text=True` ⇒ `stdout=0`；去掉 `text=True`（bytes）⇒ `stdout_bytes=459`。且 `env=None` / `env=dict(os.environ)` / `env=PATH+SystemRoot` / `shell=True` / 经 bash **全部为空** ⇒ 唯一变量就是 `text=True`。
- **修法**：bytes 模式 + 手工 `.decode("utf-8", errors="replace")`。
- **出处**：这就是 skill 04 C13 条预警的"**`subprocess(text=True)` 依赖 UTF-8 环境变量，会话外必崩**"。**读过不等于不会踩。**

## P2 · 裁判启动失败被当成 REJECT

- **症状**：一整批 `gcc=REJECT`（实际 gcc 根本没跑起来）、`vitro=?`。
- **根因**：把「启动失败 rc=-1」与「裁判拒绝 rc=1」写进同一分支；计划任务环境缺 `gcc`/`bash`（用户 PATH 不继承），`FileNotFoundError` 被吞。
- **修法**：`run()` 区分 `FileNotFoundError`(-1) / 其他异常(-2) / 正常 rc；**未知一律 `JUDGE_ERROR`**，并把 rc、stdout 长度、stderr 片段拼进标签。**禁止静默降级为 REJECT。**

## P3 · `vitro` 的 rc 被误当"启动成功与否"

- **症状**：一整批正常的"编译失败"被判成"环境坏了"。
- **根因**：`vitro` 的 rc 是**编译结果**（0 通过 / 1 有错误 / 3 壳降级），不是进程健康度。
- **修法**：**无条件解析 stdout 的 JSON 帧**，看帧里的 `ok`；rc 只作旁证。

## P4 · 只认一种帧形状 ⇒ 另一批全变 `no-ok-field`

- **症状**：一部分判据正常、一部分 `no-ok-field`，无规律。
- **根因**：帧有两种包装 ——
  `{"type":"diag","frame":{"id":N,"ok":<命令成功>,"result":{"ok":<编译结果>,"diagnostics":[…]}}}`
  只查 `frame.result.ok` 时，**无 `result` 包装**的帧（以及顶层裸 `ok`）就漏了。
- **修法**：三种形状都认（`frame.result.ok` → `frame.ok` → 顶层 `ok`），并取 `diagnostics` 的码。

## P5 · 判据基线在跑的过程中漂移

- **症状**：同样的最小复现，**几分钟前 REJECT、现在 ACCEPT**（或反之），且"看起来"稳定。
- **根因**：**多会话共写同一工作区** —— 另一会话正在改码并重建 `vitro.exe`（实测 mtime 在批跑中途变了），工作区 `git status` 同时有 8+ 文件在改。
- **修法**：**判据冻结**（复制自足快照 + 记 sha256 + 每条结果写 `judge_id`，快照变了整批重判）。见 `references/01` 的目录布局与 SKILL.md「判据冻结」。
- **顺带**：`git rev-parse HEAD` 必须**开场就查**——否则会把"已闭环的缺口"当成新发现。

## P6 · 关思考写错开关 ⇒ 吐不出代码

- **症状**：日志连续「截断/空，重试 1/2/3」；服务日志 `n_tokens ≈ max_tokens`。
- **根因**：Qwen 系关思考是 **`enable_thinking`**，写成 gpt-oss 的 `reasoning_effort` ⇒ 思考没关，token 全烧在思考上（实锤：2676 token 用尽，只落 91 字节 `typedef`）。
- **修法**：两个键都发 + 400 时逐级降级。

## P7 · 长任务输出过管道 ⇒ 看不到进度

- **症状**：命令行像卡死，其实在跑。
- **根因**：`... | tail -20` 会缓冲输出。**本规程里踩了三次。**
- **修法**：长任务**直接写日志文件**，另起一个看板/心跳线程定时刷进度文件。

## P8 · 被测 exe 陈旧 ⇒ 用旧代码下结论

- **症状**：判据结果与源码改动对不上。
- **根因**：`_build/native/.../vitro.exe` 的 mtime 早于源码改动（壳会扫 7 个目录并 stderr 大字告警，但**不阻断**）。
- **修法**：冻结快照（P5）天然规避；若要跟当前树，先重建再判。

## P9 · 复活一个已被修的历史发现

## P11 · clang golden 用 `-O2` ⇒ 方向级假 `run_mismatch`

- **症状**：BIN（二分/牛顿）方向 6/8 采样 `run_mismatch`，差异全是浮点末位（`2.73432e-16` vs `4.44089e-16`、`0.0` vs `-0.0`），看起来像「vitro 浮点语义缺陷」。
- **根因**：golden 用 `clang -O2` 编译。**`-O2` 常量折叠走 MPFR 无限精度中间值**——`x*x-2.0`（x 为 const 局部）被折叠成 `2.73432e-16`；运行时（`-O0`、SSE2、vitro 解释执行）都是 `4.44089e-16`。判据把「折叠值 vs 运行值」的差异当成了 vitre 缺陷。
- **证据**：`clang -O0` 与 vitre 逐字节一致；`clang -O2` 差；`min/r5_ulp.c`（字面量解析 / 乘法 / 加法）双端逐位一致（排除 VM 算术问题）。
- **修法**：运行轨 golden 一律 `clang -w -O0`。**-O0 重判后 BIN 5/8 转 MATCH**，仅余 q36_27b s2 两行 `b-a` 1 ULP（真信号，#152）。
- **推论**：任何「浮点末位差」先问「golden 是不是 -O2」再问 vitre。

## P12 · 运行轨三类系统性噪声（地址 / 非 ASCII / CRLF）

- **症状**：RETP 方向「四模型系统性命中」8 条 RUNDIF；MIXA/LNK 中文样本 RUNDIF。
- **根因**（都不是缺陷）：
  ① 模型打印指针地址（`%p` / `(void*)p` / 强转整数）——跨实现地址空间必然不同；
  ② 非 ASCII 输出撞 **#112**（`output.delta` 逐字节 Latin-1 折回，已知通道行为）——clang UTF-8 输出与折回后的 delta 直接比对必差；
  ③ Windows clang 输出 CRLF。
- **修法**：① 两侧 `0x…` / `0000…` 掩码为 `<ADDR>` + 提示词禁打印地址；② golden 侧 stdout 按 `latin-1` decode；③ norm 时 rstrip。修正后 4 假信号全 MATCH、4 真信号全保留（双向证绿）。
- **教训**：「跨模型多方向命中」先逐条看 diff 再定性——本批最强的「系统性」结论差点是两个判据 bug 制造的。

## P13 · 批次被 llama-server 崩溃硬杀（无 DONE/FAIL 标记）

- **症状**：任务 State=Ready 但无 `DONE.txt` / `FAIL.txt`，日志停在半路（实锤两次：10-17 23:28、10-18 01:57，均在 gpt-oss-20b 段，`ConnectionResetError 10054`）。
- **根因**：llama.cpp b11565 + gpt-oss-20b-MXFP4 长跑后静默崩溃（server 日志无 error）；python 顶层 `try/except` 都没触发 ⇒ **进程被拖死/硬杀，不是脚本异常**。
- **修法**：① 断点续跑天然无损（done 集合按 judge_id 过滤，NO_CODE 不计入）⇒ 重注册计划任务即可；
  ② 无人值守场景装**看门狗**：recurring 计划任务每 5 分钟巡检，主任务 Running 但日志停更 >10 分钟 ⇒ 杀残留（按命令行匹配）+ 重注册主任务；`DONE.txt` 出现则自停。参考实现 `tmp/llm_probe_20261018/watchdog.ps1`（注意：**.ps1 必须 UTF-8 BOM**，PS 5.1 对无 BOM UTF-8 按 ANSI 解析会乱码）。
  ③ 单模型连续崩 ⇒ 换端口重注册往往可再跑一段（端口异常占位）。

## P15 · 判据噪声：`const int n = 12; T a[n] = {...}`（GNU 扩展）

- **症状**：MST 方向 2 个模型 `vitro_reject_clang_accept`，vitro 报 `E0 变长数组(VLA)不支持初始化列表`。
- **根因**：`const int` 在 C 中**不是**常量表达式 ⇒ 这是 VLA，C99 6.7.8p3 明令 VLA 不得初始化；
  **clang/gcc 用 GNU 扩展接受了**，vitro 拒绝反而符合标准。
- **修法**：判 `vitro_reject_clang_accept` 前先看 vitro 的诊断消息；若消息是「VLA 不支持初始化列表」之类**标准禁止而 GNU 放宽**的构造 ⇒ **不计缺陷**（记入报告「撤回」栏）。
- **同理类族**：零长数组 `int a[0]`、VLA 初始化、`case` 浮点标签等 clang/gcc 扩展面，都会把正确拒绝误报成误拒。

## P16 · 静默错值的"最后一厘米"：先做变体矩阵再下定性

- **症状**：同一段「看起来是算法写错」的 RUNDIF（DIJ 距离全 2），最小复现却「不复现」。
- **根因**：触发条件比直觉窄得多——本例是**块作用域 `static` 二维数组 + 嵌套大括号初始化器**：
  只写入每个子初始化器的首元素（`{{1,2,3},{4,5,6}}` ⇒ `1,4,0,0,0,0`；double ⇒ 全 0），
  而**扁平写法 `{1,2,3,4,5,6}`、自动存储期、文件作用域、一维、char 元素、struct 数组全部正确**（#171）。
- **修法**：最小复现**不要只写一个**，要一次铺 8–10 个变体矩阵（存储期 × 维度 × 括号形态 × 元素宽度），
  矩阵跑完触发面自然收敛；否则要么漏报，要么把真缺陷当"不复现"丢掉。
- **连带教训**：模型写 `static const int graph[N][N]` 是算法题**主流写法**，命中率被严重低估——本批只有 1 例自然命中，但确定性 100%。

## P17 · 静默错值的"存储期 × 容器"矩阵：裸数组对、struct 成员错

- **症状**：MATRIX 方向 3 模型 5 样本输出全错，vitro 侧矩阵变成「每行只剩首元素」（`{{{1,2,3},{4,5,6}}}` → `1,4,5,6,0,0`）。
- **根因**：**struct 成员是多维数组 + 自动存储期 + 嵌套大括号初始化器** ⇒ 写入按错误 stride 落点（#179）。
  逐项对照（8 变体全错 / 5 变体全对）才收敛出来：
  | | 裸数组 | struct 内嵌一维 | struct 内嵌多维 |
  |---|---|---|---|
  | 自动存储期 | ✅ 正确 | ✅ 正确 | ❌ **错** |
  | static 局部 | ❌ 错（#171） | — | ✅ 正确 |
  | 文件作用域 | ✅ 正确 | — | ✅ 正确 |
- **教训**：这两条（#171 static 裸数组 / #179 自动 struct 成员）**互补**，单看任一条都会以为「某存储期 OK」。
  以后遇到「初始化值少了/错位」，必须把矩阵两维都铺满才下结论。

## P18 · 合法 C 被拒的两个高频面：brace elision 与 `'\"'`

- **brace elision**：`struct M { int d[2][3]; }; struct M m = {1,2,3,4,5,6};` —— clang/gcc 收（C99 6.7.9p20 允许省略内层大括号），
  vitro 报 `E3006 结构体初始化类型不匹配` + `W3005`（#180）。
  **陷阱**：裸数组 `int m[2][3] = {1,2,3,4,5,6};` 在 vitro 下是**正确**的 ⇒ 不能因为裸数组通过就判定「子集不支持省略大括号」。
- **字符常量 `'\"'`**：字符串里的 `\"` 正常、字符常量形式的 `'\"'` 报 `E1001 未知字符转义`（#181）。
  JSON / CSV / 词法分析器类程序里 `'\"'` 是标准写法，命中率很高。
- **判据**：`vitro_reject_clang_accept` 不要一律当「误拒缺陷」——先看诊断码：
  `E0 变长数组不支持初始化列表`（P15）、`E3073 本引擎未实现标准库函数`（strtok 等库面排除）是**设计内**，
  `E3006` / `E1001` / `E3014` 这类则是**实现漏项**。

## P20 · 四类「看着像缺陷、其实是边界/噪声」的固定答案

定性前逐条对一遍，能省掉大半假信号：

| 症状 | 真相 | 依据 |
|---|---|---|
| 打印 `isupper`/`isdigit` 等 ctype 返回值，clang 得 `1/2/4/8`、vitro 得 `1` | **实现定义**，C 标准只要求非零 | 第八批 smoke；提示词已禁「直接打印 ctype 返回值」，要打印就写 `(isupper(c) != 0)` |
| `E0 全局数据区容量不足（上限 61440 字节）` | **沙盒设计**（60KB 全局/BSS 闸），大表必须走堆 | 第九批 TEXTWRAP 两条；提示词下批须写「全局/静态数组总量 ≤ 60KB，大数组用 malloc」 |

| `E3029 print_int 参数必须是 int` | **保留名冲突**（`print_int` 是引擎内建） | skill 03 实锤反例之一；模型自定义同名函数会撞 |

## P21 · 模型自己把 golden 弄脏时，RUNDIF/trap 一律不算证据

- **症状**：一批里 `run_mismatch` 与 `run_not_finished` 特别多，看着像引擎大面积出问题。
- **实测（第八批撤回 5 条）**：
  ① clang golden 自己打印 `Verification: FAILED` / `Success: NO`（模型 round-trip 逻辑有 bug）⇒ 该样本不是好 golden；
  ② 模型 `char matrix[100][3]` 未初始化就打印 ⇒ UB，clang 侧读到残留（`Attack ` / `é`）而 vitro 读到 0，「谁对」无意义；
  ③ vitro trap 命中的是**模型自身越界**（`queue[tail++]` 没边界检查、`hist_sharp[10]` 越界）⇒ vitro 是**正确拦截**，不是缺陷。
- **判据**：`run_not_finished` / `run_mismatch` 定性前必须做三步——① 看 golden 里有没有 `FAILED/NO` 字样；
  ② 看 trap 行是不是模型自己越界/未初始化；③ 看分母/下标是不是被上游缺陷喂成 0（**次生现象**）。
- **次生链实例（第九批 LONG13）**：`char fields[][N]` 形参 stride 错（#193）⇒ CSV 字段全 0 ⇒ `grand_total=0`
  ⇒ 除法 trap「double 除以零」。若只看 trap 文本就会误归因到 #163（IEEE 754 除零），实际根因在 #193。

## P22 · 二维数组形参：`char` 元素会丢 stride，`int` 元素正常

- **症状**：CSV/棋盘/字符串表类程序传参后 `a[1]` 起就错（trap 或静默错值），但 `int` 二维数组同写法正常。
- **根因**（#193）：`char a[][N]` / `char (*a)[N]` / `const char a[][N]` / 三维 `char a[][4][N]` 传参后，
  `a[i]` 按 **1 字节**步进而非 N 字节 ⇒ `char[8]` 被当成 `char`。
  局部使用正常、一维正常、`int[][N]` 正常 —— 三组对照必须都跑，才敢断言是「char 形状退化」而不是「多维传参整体缺失」。
- **最危险形态**：**全局**二维 char 数组传参 ⇒ 地址高、越界不撞沙盒边界 ⇒ **不 trap、静默错值**。
- **修好前的规避**：探针提示词里让模型用「一维缓冲 + 手工下标 `buf[i*N+j]`」，或把二维表做成 struct 成员按引用传。
- **连带**：这类错位常常不在本层炸，而是在下游以「除零 / 数组越界 / 空字符串」的形式暴露（P21 的次生链）。

## 一句话总纲

**能被证伪的数字才是数字；而让数字可被证伪的前提是——先把判据本身钉死。**
