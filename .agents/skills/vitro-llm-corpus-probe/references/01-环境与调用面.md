# 01 · 环境与调用面（Windows）

探针必须在**计划任务**里跑（会话内进程启动税 ~145ms 会污染一切性能/时序口径，见 skill 04 C12–C14）。但计划任务环境与交互式会话**不同**，本节是实锤清单。

## 计划任务的最小正确姿势

```powershell
$py  = "<python.exe 绝对路径>"
$a = New-ScheduledTaskAction -Execute $py -Argument '"<脚本绝对路径>"' -WorkingDirectory "<cwd>"
$t = New-ScheduledTaskTrigger -Once -At (Get-Date).AddMinutes(1)     # ★ 延时触发器，让服务自己点火
$s = New-ScheduledTaskSettingsSet -AllowStartIfOnBatteries -DontStopIfGoingOnBatteries `
        -ExecutionTimeLimit (New-TimeSpan -Hours 10) -StartWhenAvailable -MultipleInstances IgnoreNew
Register-ScheduledTask -TaskName "<name>" -Action $a -Trigger $t -Settings $s -Force
```

**坑**：
- **禁调 `Start-ScheduledTask`**——立刻启会被 `0xC000013A` 杀掉，脚本第一行都跑不到。**必须延时触发器**。
- **`AtStartup` / `AtLogOn` 触发器需要管理员权限**，非提权会话 `Register-ScheduledTask` 报「拒绝访问」⇒ 重启后任务不会自己回来；备一个「重新点火」的 `.ps1` 给人双击。
- **一次性触发器只能烧一次**：跑完 `NextRunTime` 为空，要重启就 `Register-ScheduledTask -Force` 重注册。
- **改已注册任务**（`Set-ScheduledTask`）也要提权 ⇒ **改脚本 + 重新注册**是唯一路径。
- **完成信号写文件轮询**，别信 PowerShell 的 stdout（常不回显）；诊断用 `Get-ScheduledTaskInfo`，但**它在 PowerShell 工具里会被截断**，落文件再读更稳。

## ★ 会话外脚本的两条硬规矩（2026-10-14 实锤）

**① 顶层 `try/except` + `traceback` 落日志 —— 任务环境里 stderr 也会丢。**

未捕获异常的表象只有三样：**日志停在半路**、任务信息里的结果码 **1**、**没有任何报错文本**。
⇒ 编排脚本末尾一律写成：

```python
try:
    main()
except Exception:
    import traceback
    log("!! 未捕获异常：")
    for line in traceback.format_exc().splitlines():
        log("   " + line)
    raise
```

这一条是把 skill 04 的 C13 教训**推广到「进程整体失败」**：不只是 stdout 会丢，**stderr 也会**。

**② 数据与模板路径先离线跑通再花模型时间。**

把提示词 JSON 全量格式化一遍、断言长度要求存在；否则一个键名打错就白等一整轮。
**「先花 5 秒离线验证」永远比「花 40 分钟等一轮再发现打错字」便宜。**

## 从 Bash 工具调 PowerShell 的坑

- 长命令**输出会被截断**（表现为"命令写了一半就没输出"）⇒ **一条命令只做一件事**，结果 `Out-File` 到文件，再用 Read/cat 读。
- 杀进程要**按命令行精确匹配**，别按名字——否则会误杀自己：
  ```powershell
  Get-CimInstance Win32_Process | Where-Object { $_.CommandLine -match "gen50\.py|llama-server" } | Stop-Process -Force
  ```
  （按 `-Name python` 会连工具自己的 pwsh/python 一起杀。）

## 判据调用：直调两臂，不走壳

```python
NATIVE = "<judge_dir>/vitro.exe"                        # native 臂
NODE   = r"C:\Program Files\nodejs\node.exe"            # node 显式绝对路径
WASMJS = "<judge_dir>/scripts/vitro_cli/main.js"        # wasm 臂
```

- **不要经 `scripts/bin/vitro` 壳**：壳每次全树扫 `moonbit/**/*.mbt` 的 mtime 防陈旧制品，单次 ~500ms（37× 于直调）。批量场景直接调臂二进制。
- **native exe 自足**：导入表只有 `KERNEL32/SHELL32/bcrypt/dbghelp`，复制到任意目录、任意 cwd 都能跑。
- **wasm 壳不自足**：`main.js` 用 `REPO = path.join(__dirname, "..", "..")` 定位 `moonbit/_build/wasm-gc/release/build/gateway/wasm/wasm.wasm`，并 `require("./api_help.json")` ⇒ 复制时必须**按原相对布局**摆。

## `subprocess` 三坑（都会静默产生假结果）

1. **禁 `text=True`**：计划任务里它把 stdout 读成**空串**（bytes 模式同调用正常）。手工 `.decode("utf-8", errors="replace")`。
2. **`env` 不参与可执行文件查找**：Windows 上 `subprocess` 用**当前进程 PATH** 找 exe ⇒ 一律绝对路径。
3. **计划任务环境没有用户 PATH**：`gcc`（`D:\code\mingw64\bin`）、`bash`、`node` 都可能不在 ⇒ 要么绝对路径，要么显式拼进 `env["PATH"]`（后者只对被调用的壳有效）。

## llama-server 起停

```bash
llama-server.exe -m <model.gguf> --host 127.0.0.1 --port <P> -ngl 999 -c 8192 --jinja
```
- 就绪探测：轮询 `GET /v1/models`，同时**检查子进程是否已退出**（`p.poll() is not None` ⇒ 起不来，别等到超时）。
- 一个模型跑完必须 `terminate()` + `kill()`，否则下一个模型加载时显存/内存冲突。
- 服务日志单独落文件（`gen50_server_<tag>.log`），排查"生成慢/吐不出代码"全靠它（看 `n_tokens` 与 `eval time`）。
