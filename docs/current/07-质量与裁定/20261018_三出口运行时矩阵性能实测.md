## 1. 出口级逐进程矩阵（CLI 端到端，pure ms，5-7 轮中位）

| 组合 | run fib20 | run bubble200 | run nested500 |
|---|---|---|---|
| native（exe） | 25.4 | 146.3 | 462.2 |
| js × node | 82.1 | 235.7 | 656.5 |
| js × bun | 88.6 | 340.6 | 1063.8 |
| js × deno | 57.6 | 211.0 | 616.8 |
| **wasm × node** | **24.7** | 83.7 | 186.6 |
| wasm × bun | 36.7 | 95.9 | 302.3 |
| wasm × deno | 40.6 | 51.6 | **185.1** |

- **wasm 出口对 js 出口（同 node）：快 2.3–3.5×**（nested 186.6 vs 656.5 = 0.28×）。
- **wasm 出口对 native：nested 快 2.5×**（185–187 vs 462），与实录 §16.2 的 0.30× 基线吻合。
- 短场景（rfib ~25ms）逐进程口径噪声大（50ms 会话税残差），长场景（rbub/rnest）可信。
- compile 场景（cfib/cbub）单次 5–15ms 被启动税淹没——编译面用 invoke/libprobe 口径（下两节）。

## 3. 库级引擎纯算（libprobe：直调 lexer/parser/typeck/codegen/vm，无壳无 wire）

| 场景 | native | js node | js bun | js deno | wasmtime（wasm-gc） |
|---|---|---|---|---|---|
| s1 lexer ×400 | **8.3** | 35.5 | 45.5 | 44.5 | – |
| s2 compile fib ×200 | **11.6** | 57.1 | 70.9 | 68.8 | – |
| s3 run fib20 ×10 | 241.9 | 349.9 | 530.1 | 332.1 | **192.7** |
| s4 run nested300 ×3 | 501.5 | 610.5 | 1116.5 | 577.9 | **409.7** |
| s5 run count5m（9500 万步） | 708.0 | 1038.2 | 3664.0 | 1035.8 | **634.8** |
| s6 GC 压力 ×200 | **2.2** | 10.1 | 10.5 | 5.9 | – |
| s7 run bubble200 ×3 | 374.1 | 511.9 | 934.9 | 501.9 | – |

- **wasmtime（Cranelift）执行层三场景全面第一**（0.80–0.90× vs native），其中 **s5 长直线循环 634.8ms = 1.5 亿步/s**。
- **wasmtime vs V8（wasm-gc 引擎同产物）两极分化**：s5 长循环快 ~4.7×（V8 外推 ~3000ms，源自 invoke count20m 12s/3.8e8 步）；s3/s4 调用/GC 密集反而慢 1.8–2.1×（V8 s3 外推 ~109ms）——Cranelift 对直线循环代码强、调用边界与 GC 交互弱。
- **bun/JSC 的 i64 灾难**：s5 用 `long long`（js 臂 i64 = f64/BigInt 模拟路径），bun 3664ms vs node 1038ms = **3.5×**；纯 int 场景（s3/s4/s7）bun 只慢 1.5–1.8×。
- 编译管线 native 基准最快（8.3ms/400 token×400？口径见 libprobe s1/s2），js 臂 ~4–5×，bun/deno 再慢 ~25%。
- js 引擎 vs wasm-gc 引擎（同为 V8/node）：invoke nested 182ms（wasm）vs CLI rnest 656ms（js，同 25 万次迭代量级）→ **wasm-gc 引擎快 ~3.5×**。

## 4. wasmtime 专项（「wasmtime 对 wasm-gc 的加持」）

- **gateway 产物（773KB）无法进 wasmtime**：`unknown import: _::`——js-string builtins（`builtins:['js-string'], importedStringConstants:'_'`）是 JS 引擎专属提案，wasmtime 不提供。这是**协议通道级**的不可用，非 GC 提案问题。
- **绕过形态实测可行**：libprobe 零-import 探针（无 js-string、无 env/println FFI）wasmtime 49.0.3 直接加载运行成功（GC 提案 ok）。⇒ 若要 wasmtime 臂，需要一个独立的非 js-string 出口形态（如 native 式 CLI 直连，协议不经 gateway 字符串通道）。
- 性能定性（§3 表）：**长算循环场景 wasmtime 有真加持（~4.7× vs V8、1.1× vs native），交互/调用密集场景劣于 V8（1.8–2.1×）**。教学负载（短程序、单步/帧流交互）不受益；批处理/长作业（判题、语料跑批）受益。

## 5. #133 止血方案性能影响（预算墙撑开 1e7 → 2e9/2^31-1）

**CLI 通道（count5m ≈ 9500 万步，5 轮中位）**：

| 臂 | 默认（1e7 截断）rc=3 | `--max-steps 2000000000` rc=0 | `--max-steps 2147483647` rc=0 |
|---|---|---|---|
| native | 888ms | 8138ms | 8511ms |
| js-node | 1492ms | 12413ms | 12698ms |

- **截断态吞吐 = 全程吞吐**：native 前 1e7 步折算 857ms vs 实测 888ms（+3.6%）；js 1307ms vs 1492ms（+14%，含截断后处理）→ **预算上限检查零热路径开销**；2e9 与顶格两档差 4.3–4.6%（噪声内，cap 值无关性能）。
- **截断罚款一次性且小**（rc=3 路径的 trap 帧 + #133 报错分家文案 + inspect 最近 10 万步变量扫描）：native ~31ms / js ~185ms。
- **gateway 通道（count20m ≈ 3.8 亿步，node）**：显式 `max_steps:2e9` / 顶格 2^31-1 / `preset:"algo"` 三态各两轮全部跑完（ok:true，trapped:false），单次 11.6–14.3s 同量级（热噪声 ±10%）→ **preset 档位与显式键行为等价，撑开上限零吞吐代价**。algo 档真实吞吐 ~3000 万步/s（wasm/V8）。

## 6. 跨实现对照（用户问「跟其他编译器项目比如 CPython」——本批补测）

> **口径**：程序内计时（perf_counter / performance.now / QPC），§17 同源三程序 + 防常量折叠（argv 传参 + 结果跨轮累加，ACC 校验全对）。mb 侧口径 = §1/§2 已测数据（wasm = invoke 纯 run 摊扣 compile；native/js = CLI pure 差分）。CPython 3.14 默认解释器（JIT 预览未开）。探针 `xlang/`。

**单次执行耗时（ms，多轮中位）**：

|---|---|---|---|
| clang -O2（C，22.1.4） | 0.0119 | 0.0060 | 0.0825 |
| gcc -O2（C，MinGW 16.2） | 0.0054 | 0.0063 | 0.1295 |
| CPython 3.14 | 0.578 | 0.931 | 7.41 |

| deno V8（JS 直跑） | 0.0431 | 0.0182 | 0.166 |
| bun JSC（JS 直跑） | 0.0290 | 0.0204 | 0.194 |
| **mb-wasm × V8(node)** | 10.87 | 40.17 | 181.6 |

**mb / 各基准比值（每格 = wasm-node / native）**：

| 程序 | vs CPython 3.14 | vs V8-JS(node) | vs Clang -O2 |
|---|---|---|---|
| fib(20) | 18.8× / 43.1× | 238× / 545× | 913× / 2092× |
| bubble 200 | 43.2× / 156.7× | 2560× / 9293× | 6695× / 24317× |
| nested 500×500 | 24.5× / 62.3× | 1088× / 2765× | 2201× / 5598× |

- **§17（2026-10-04）定性复现**：mb 的 VM 全速执行落后 CPython（纯解释器）10–60×、落后 V8-JS 两到三个数量级、落后 Clang-O2 三到四个数量级——短板在 VM 解释循环本身（nested 零内存访问也慢 24×+，非内存检查/插桩的锅；issue #41 在档）。
- **比值较 §17 扩大的主因是分母提速**：CPython 3.14 的新解释器分派使整数循环大幅变快（bubble 2.46→0.93ms = 2.6×、nested 13.8→7.41ms = 1.9×；fib 递归 0.515→0.578 持平）；mb 侧 nested 变慢（132→182ms）再叠加——§2 的 +37% 可疑漂移在比值口径下同样显形。
- gcc 16.2 对固定递归 fib 出 5.4μs（clang 11.9μs 的 2.2 倍快，ACC 正确）——新编译器对自递归的激进优化，趣味点仅作记录。
- JS 直跑侧 JSC/V8 各有胜负（fib JSC 快 1.6×、nested V8 快 1.2×），与 §3 的 wasm-gc 执行侧「bun 全面慢」不同构——**JSC 弱的是 wasm-gc 执行与 i64 模拟，不是 JS 本身**。

## 7. 方法与坑（新批）

1. 会话启动税本会话 ~50ms（非 148ms——实录 §12.1 那批是 workbuddy 会话特有）；口径照旧：场景 ≥300ms + boot 逐对交替。
2. `@env.args()` 两端语义不一致：native 含 exe 名、js 含 node+脚本全量（moon js 运行时不剥）——场景号分发用**末参**通吃；驱动必须断言 ACC 输出（本轮首跑全臂空转假绿被 ACC 校验抓回）。
3. deno 跑 CJS 探针须 `.cjs` 扩展（deno 2.9 对 .js 默认 ESM，auto-detect 未开）；bun 原生通吃。
4. wasmtime 不可加载 js-string builtins 产物（`_::` imports）；零 import 探针形态可行。
5. bubble200 排序输出是 `1 200`（升序结果）非输入残留 `199 0`——期望值要先跑真值。
6. mklink junction 在 Git Bash 单引号里 `\\` 不折叠——用双引号。
