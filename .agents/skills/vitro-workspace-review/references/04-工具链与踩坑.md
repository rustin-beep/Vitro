## A · MoonBit 工具链

| # | 坑 | 表现 | 处置 |
|---|---|---|---|
| A1 | **`moon check` 偶发文件锁冲突** | `Sys_error("...\\_build\\...\\*.ast: Permission denied")`，整轮报 `failed to run check for targets [...]` —— Windows AV / Defender 抢 `_build` 文件锁 | **直接重试一次**即绿，与代码无关；**别据此判"构建失败"**（多次实证） |
| A2 | **缺 `moon.pkg` 的目录不被视为包 ⇒ 静默成功** | `moon build --target native <dir>`：零输出、**EXIT=0、零产物**；`check` 同样静默（`no work to do`） | `<dir>` 是**目录过滤器**，判包依据 = **该目录有无 `moon.pkg`**。⇒ **别拿 EXIT=0 当成功**，要 `find _build -name "*.exe"` 验证产物 |
| A3 | **`moon.pkg` 内容必须是合法变体** | `pkgtype(kind: "lib")` ⇒ `unknown variant 'lib', expected one of library, executable, foreign_library`；空文件 = 默认 library ⇒ `fn main` 报 `[4069] Unexpected main function in the non-main package` | 可执行工程写 `pkgtype(kind: "executable")` |
| A4 | **`moon test` 失败不打印实际值** | 只报 `FAILED` 行 | 用 `fail(s)` 把实际值打出来（`assert_eq` 失败不含值） |
| A5 | **增量编译漏检** | 连续快速改写同一文件，工具链可能复用旧产物（Windows 同秒时间戳）⇒ 假绿 / 假红 | 注入与测试之间 **`sleep ≥1.5s`**；首轮结果不可信时重做 |
| A6 | **`moon fmt --check` 本机 exit 127** | `failed to execute git --no-pager diff --no-index` | **别把 127 读成"格式没问题"**。CI 口径是 `moon fmt` + `git diff --exit-code`，见 `02` 的 D13 |
| A7 | **`moon test -p <pkg>` 的 Total 是单包数** | 与全仓总数对不上 | 先确认口径再判错；往包里加探针文件会让它 +1，**记得从基线里减掉** |
| A8 | **`moon check` / `moon test` 不会顺手刷新 `.mbti`** | 跑完 `git status` 仍干净 | ⇒ CI 里 `mbti_sync -check` 的顺序判据可信（这是**要实测**的结论，别假设前面的步骤会顺手修好） |
| A9 | **区间语法** | `for _ in 0..3` 报 `Missing '=' after '..'` | 写 `0..<3`（或 `0..=2`） |
| A10 | **浮点字面量必须带小数点** | `1e23` 语法错 | `1.0e23` |
| A11 | **core 包要显式 import** | 用 `@env` / `@fs` 只警告但会连带报错 | 在 `moon.pkg` 的 `import { "moonbitlang/core/env" }` 里声明 |
| A12 | **`raise` 需真 error 类型** | `raise "字符串"` 编译错（`String is not an error type`）；`fn main raise` 不允许 | 声明 `priv suberror E { Fail(message~ : String) }`；入口用 `fn main` + `try/catch` |
| A13 | **dump 类工具"成功"也可能失败** | CLI 打印成功但产物里 `ok:false` | 必查产物的 `ok` 字段 |
| A14 | **`String::length()` 是 UTF-16 码元数，不是 UTF-8 字节数** | `@utf8.encode(s)[:s.length()-1]` 会切进多字节序列 ⇒ `decode` 抛错 ⇒ `catch { _ => "" }` **静默产空串** | 用 `let b=@utf8.encode(s); @utf8.decode(b[:b.length()-1])` |
| A15 | **扫描 / 统计脚本必须排除 `_build`** | `__generated_driver_for_*_test.mbt` 含大量重复 | 否则把生成代码误判成"自研代码重复" |
| A16 | **`moon check` warning 数量可当回归信号** | 不卡 CI，故容易被忽略 | 审"修复批"时比改前 / 改后总数，把增量落到 `文件:行` |

| A17 | **`moon.mod` 的 `import` 必须带版本号** | `import { "vitro/engine" }` ⇒ `Failed to resolve the module dependency graph: moon.mod only supports versioned registry dependencies` | 接**本地工作区**当依赖：写 `"vitro/engine@<本地 moon.mod 的 version>"` + 在 `.mooncakes/<owner>/<mod>` 建**目录联接**指向本地模块目录（PowerShell `New-Item -ItemType Junction`）。实测可编到本地 HEAD 码（2026-09-29） |

| A18 | **`moon.work` 工作区才是"依赖本地工作树"的正解；它缺失时静默降级到 registry 且仍全绿** | ① `moon.mod` 里写路径（`import { "../x" }`）⇒ 硬错 `moon.mod only supports versioned registry dependencies in \`import\``。② 改写成版本式 `"mod@ver"` 但**不建工作区** ⇒ `moon check` 0 errors、`moon test` 全绿、**打印输出与工作区模式逐字相同**，`moon tree` 却显示解析到 registry 制品（无 `[workspace member]` 标注），任务数明显更少（实测 28 vs 70）⇒ **假绿**，见 `03` 的 D16。③ 工作区成员**覆盖** import 里的版本要求：连写 `@9.9.9` 也只给一条 warning 就解析到工作树 ⇒ 该版本字面量**不参与解析**，**不可当版本 pin / 不可当"测得是哪个版本"的证据**。 | 建 `moon.work`：`members = ["<相对路径到本地模块>", "."]`（`moon work init <path>` 会把成员写成**绝对路径**，要手工改相对才可入库；相对路径实测可用）。用 `moon tree` 复核：必须出现 `-> <pkg>@<ver> (local <工作树绝对路径>) [workspace member]`。**凡"依赖本地工作树"的构建/测试，日志里必须能读到工作区成员解析行；只看到 "0 errors / 全绿" 不算证据。** 上游报错文本自带指路（`use workspace configuration in \`moon.work\` instead`）。注：`03` 里 A17 记的 `.mooncakes/<owner>/<mod>` 目录联接是另一条可用路径，两条不要混用 |

| A19 | **跨包 struct 字段只读（`mut` 写权限仅限定义包内；字段默认 public）** | 在包外对另一包的 struct 字段赋值 ⇒ `Error [4094] Cannot modify a read-only field: <f>`——**即使字段声明带 `mut`**；给它加 `pub` 也无效，且报 `Warning (redundant_modifier): ... field <f> is public by default`（⇒ 字段**默认即 public**，跨包**可读**，故读取类断言照常过，只有写入被拒） | 迁移 / 跨包复用代码时，任何"由包外写字段"的语句必须改写成**显式参数 / setter 调用**；跨包可写只能用 **struct 级 `pub(all)`**（本仓 protocol 全字段 `pub(all)` 的先例）。审"迁移批"时逐条核被静默删除 / 改写的跨包赋值——它们常被当作"零语义变更"漏掉（实测：`vm.step_count = st` 在 time_travel 包报 read-only） |

| A20 | **`abort`（panic）不可被 `try/catch` 捕获；`@test` 包无 panic 断言 API** | 写 `try { abort(...) } catch { _ => caught = true }` 探针 ⇒ 测试直接判 `failed: Error`（catch 不生效）；查 `~/.moon/lib/core/test/pkg.generated.mbti` 只有 `assert_raise` / `expect_error`（形参 `() -> T raise E`，**只针对 `Error`**），**无** `expect_panic` / `assert_panic` | ⇒ 实现里所有 `guard … else { abort(...) }`（fail loud 的非法输入分支）在单测中**结构性不可锚**——**别再报"这里缺锚"**；判"某 abort 分支无锚"前**先查 API**，不要凭印象说"应该能测"。要可锚需改用 `raise`（可捕获的 `Error`，代价是丢失进程级 fail-loud 语义）或工具链补 panic 捕获 API |

| A21 | **`moon build` 产出的可执行文件是独立构建物，源码还原后不重建就会测到陈旧/注入态产物** | 做"改坏 → 跑 → 还原"的注入实验时，若被测对象是 `moon build --target native <pkg>` 产出的 exe（如 `cmd/serve` 服务进程），**`moon test` 的编译不会更新它** ⇒ 探针把**上一次注入态**的 exe 当成品跑 | 每次还原源码后**显式重建被测 exe** 再复测。判据：同一探针在"重建前 / 重建后"两次结论不一致 ⇒ 前一次测的是陈旧 exe。**别只看 `git status` 干净就以为产物也干净**（2026-10-02 实测：还原源码但漏重建，探针给出 45/45 全同的**假 SAME**，重建后真实分叉 26/45） |
| A22 | **`moon check --target all` 首跑可能报 `failed when checking project`——A1 文件锁瞬态** | Windows 并发构建 / Defender 锁目标文件，首跑瞬时失败、复跑即绿 | 判"真错"前**复跑一次**；连续两红才按真错处置（同 clang_direct 首跑 127 例瞬态误判的家族） |
| A23 | **demo_smoke 必须 node 25**（node 22 下 wasm-gc 的 string-constant import 直接崩） | CI 已 pin 25；本地 PATH 常是 22 | 本地跑用完整路径 `"/c/Program Files/nodejs/node.exe"`（v25）；node 版本不符的崩溃形态是 import 段报错而非测试失败，勿误判为引擎回归。**同族面（2026-10-07 补）**：统一入口 `scripts/bin/vitro` 与六防线 `--backend wasm` 臂在 node < 25 时形态不同——launcher **exit 3 降级 native**（stderr 明示 `backend=`），双臂对拍闸与 wasm 臂**全假红**；显式 `PATH="/c/Program Files/nodejs:$PATH"` 用 node 25 才得真值 |
| A24 | **本 agent 环境里 headless chromium 起不来** | `--dump-dom` 恒空文件、`--virtual-time-budget` 不自行退出（只能靠 `timeout` 杀）；stderr 报 `network service crashed or was terminated` / `Failed to create shared context` / `Cannot use V8 Proxy resolver in single process mode`。`--headless=new`、`--headless=old`、`--single-process`、`--no-zygote`、`--disable-dev-shm-usage`、独立 `--user-data-dir` **全部实测无效** | 想在浏览器里做端到端验收时**别在此环境反复试**。三条替代：① 改走"进程内直调制品"的等价探针（node 直 `import()` 产物模块验说明符 / 直接实例化 wasm 并按协议调方法验字段面）——**验不了 DOM 渲染与事件**；② 把浏览器断言接进 CI（runner 上可跑）；③ 如实登记为"未覆盖"，**禁写成"已实测通过"** |
| A25 | **moon 跨会话/跨 target 增量缓存毒化**（moonbit/AGENTS.md 陷阱 #41 同源） | 并发会话改源后，本会话 `moon build --release --target wasm-gc` 增量判定 up-to-date——产物**仍是旧代码**，而同刻 native 产物是对的 ⇒「同源不同果」酷似 wasm-gc 后端语义 bug，极易误诊 | 跨会话接过工作区后，消费 wasm-gc/native 产物做行为验证前**先 `rm -rf moonbit/_build/<target>` 强制全量重建**；「产物 mtime 新」不构成「含新代码」证据。双臂对拍（`scripts/vitro_cli_smoke`）是最便宜的行为指纹（2026-10-06 实锤） |
| A26 | **native 探针进程 0xC0000409（UCRT fastfail）的定位法**（2026-10-11 补） | 崩溃无栈无消息（fastfail 不走 raise）——常见根因：C 层 NULL stream 直传 `fwrite`/`fclose`（本仓 fs 包写方向实测）、`.unwrap()` panic、数组越界写坏运行时 | 定位三步：① `moon test` 崩溃时 moon 会打 **`Active test at executable exit`** 指认测试文件——顺藤摸瓜；② 多文件包用**逐文件二分**（注释法临时禁用测试块）隔离；③ C 侧对照：写最小 C 探针（如 `fwrite(...,NULL)`）clang 编译跑 PowerShell `Start-Process -PassThru` 取退出码验证同码。**禁在崩溃探针上反复盲试**——二分比读码快 |
| A27 | **生成器产物与格式化器闸互斥**（2026-10-11 补，`03` D8 双闸互斥同族） | 生成器产物（@generated `.mbt`/`.json`）入库时未过格式化器 ⇒ 格式化闸（`moon fmt`）要求重排产物，生成器 `-check` 幂等锁要求产物 =「现场生成」——**后落闸的那道永远红**，本地无论怎么调都无法双绿（实测：`moon fmt` 把单行 `"k" => Some("…")` 拆多行悬挂，与 `gen_api_help -check` 互斥） | **产出即合规处方**：生成器发射模板对齐格式化器期望形态，验收判据 = **重生成产物与 `fmt` 后产物逐字节一致**；新生成器接线时先干跑一次格式化器看产物 diff；形态难复刻时的退路 = 生成流程内嵌格式化（生成 → fmt → 再比对）。**手改产物对齐 fmt 是禁忌**——下次再生又打回原形 |

| A28 | **Windows 上 native 目标忽略 `MOON_CC=clang`（回落 MSVC）；且跨平台 golden 在本地不可作真值门禁** | ① `MOON_CC=clang` 下 `moon build --target native` 与 `moon run --target native` 打印 `MOON_CC is ignored for Windows MSVC direct object native target because it is not a cl-compatible driver` ⇒ **产物实为 MSVC 编的**，与 CI 基线（clang 编）不同；`printf` 实现差异即让 stdout 指纹全变。② 即便改用 `MOON_CC=clang-cl` 对齐编译器，**golden digest 在 Windows 本地仍全红**——CI 的 golden 是 Linux 产出的 LF 行尾，本地 stdout 是 CRLF ⇒ 逐文件指纹全不匹配（形态：**几乎全部用例 DIFF、只余无 stdout 的少数 SAME**，数量级与语料规模同阶） | ① native 臂要 `MOON_CC=clang-cl`（**不是 `clang`**）才真正生效；② **本地不要用跨平台 golden 判红绿**（会拿到"大面积红"的假象并误判被审批）——改走**同平台两态对拍**：修复前 / 修复后两个 worktree 各建产物，同一语料逐字节比输出；要真值就用**同平台 clang**（两边都 CRLF）而非 CI golden。③ 判「某闸红」前先分清红的是**语义分叉**还是**平台行尾 / 编译器差异**——只有前者进报告 |

| A29 | **审阅期间工作区的 `HEAD` 被并发会话切走 ⇒ 中途取的结论全部失效** | 仓内多会话并发时，另一会话会 `checkout` / `merge` / `rebase` 主工作区；审阅者中途用 `HEAD` 取「PR 的 diff / 基线」时参照物已在脚下移动 ⇒ 前后两轮测量可能分别对着**两个不同版本**，结论自相矛盾而无人察觉（实测：同一次审阅里 `git diff --numstat` 先后给出「vm digest 902 增 620 删」与「逐字节相同」两个互斥结论——真因是两次测量之间 `HEAD` 被切到了 master） | 审阅一开始就把三个参照物**钉成显式 ref**（PR tip / PR base / origin/master），此后 `git show <ref>:<path>` / `git diff <base>..<prtip>` 一律用显式 ref，**不用 `HEAD`**；每次测量前复核 `git rev-parse HEAD` 与开工时一致，不一致就重跑受影响的测量（尤以「文件被改写 / 计数变化」类为重）。另：`git status` 出现 `UU`（未解冲突）即并发会话正在动同一批文件，**不得回滚、不得在其上叠加编辑**，收尾只在报告里点名 |
| A30 | **脚本改写 `.mbt` 时把行尾写成 CRLF ⇒ moonc 报编译器 ICE，不是语法错**（2026-10-31 补，PR #403 审阅；与 `D2` 同族，但后果完全不同） | `moon test -p <pkg>` 输出 `Error: failed to build … ` 一长串 + `This is a bug in the compiler` + `Error: Invalid_argument("Moonc.Basic_ba_int.get")`（moonc 0.10.18+6c83a7f62 实测）。**任何**改到该文件的突变都复现，连 `out.push((name, 0))` 这种单 token 改动也一样，于是极易被读成"这个突变改坏了/不可编译 ⇒ 该点测不了" | 根因是改写工具的行尾转换（python `open(p,'w')` 默认把 `\n` 译成 CRLF），**不是**代码问题。判据一条：`git diff --stat` 显示**整文件**改动（几百行）即命中；对照做法——把同一突变用二进制/`newline=''` 重写一遍，**逐字相同的代码立刻编译通过**。⇒ 对 `.mbt` 做突变注入一律 `io.open(p, 'w', encoding='utf-8', newline='')`，并在跑之前确认 `git diff --stat` 只动了目标行 |

## B · 构建与工作目录

| # | 坑 | 处置 |
|---|---|---|
| B1 | **构建命令必须在 `moonbit/` 下跑** | 仓库根跑 `moon build --target native cmd/run` = `Error: not in a Moon project`（exit 127）。脚本自己的报错提示可能照抄这条错命令 ⇒ "构建失败但工具照跑旧 exe" |
| B2 | **runner exe 的新鲜度无人校验** | 跑依赖 runner 的防线前**先手动构建**；`_build/.../cmd/run/run.exe` 的 mtime 可能早于其源码 |
| B3 | **大常量表会砸进单个 `moonbit_init`** | 编译器把整个模块的全局初始化发射成一个平坦函数；大数组字面量会展开成 N 条逐元素 store。⇒ Windows 默认 `cl` 在高优化级别下会在该函数上撞优化器悬崖，而 `clang` 不会。`MOON_CC=clang` 可绕过；文件大小无关，**病在单函数语句数** |

| B4 | **全量 `moon build --release --target native` 会被 `foreign_library` + `+native` 的包卡死** | `gateway` 报 `LINK : fatal error LNK1561: 必须定义入口点`（native 后端对它仍去链可执行文件），整轮 `Failed with N warnings, 0 errors` → `failed to run build for target Native`；同期 `cmd/*` 全部正常 | 先看是不是**只有该包红**；构建改用**逐目标**形态（`moon build --release --target native cmd/run` …）。CI 若只跑该包的 wasm-gc 形态，`+native` 声明就从未被验证（2026-09-29 实锤：gateway + CI 只跑 `--target wasm-gc gateway`） |

| B5 | **`foreign_library` 包单独做 native 构建必失败** | `moon build --release --target native <fl_pkg>` ⇒ `LINK : fatal error LNK1561: 必须定义入口点`（moon 对它仍去链可执行文件），整轮 `Failed with N warnings, 0 errors` → `failed to run build for target Native`；**4 行最小模块即可复现**（与代码规模/警告数无关）。消费者（executable 导入它）**不受影响** | 两条直觉修法已实测证伪：①去 `+native` ⇒ 消费者报 `Selected backend 'native' is incompatible with the dependency graph`；②改 `pkgtype(kind: "library")` ⇒ `[4219] #export_name 只能用于 foreign library`。**可用修法 = 拆包**：核心逻辑放 `library` 包（双 target），另建只含 `#export_name` 面的 `foreign_library` 外壳（`+wasm-gc` 单目标）——全量 native 构建与 wasm 导出面同时成立（2026-09-29 实测三态全过）。**补充**：与编译器无关（`MOON_CC=clang` 下同样失败，只换成 `lld-link: error: subsystem must be defined`）；**爆炸半径 = 整个模块**（模块里只要有一个没人链接的 foreign_library，模块级 `moon build --target native` 就整体失败）；对照纯 `library` 包单独构建 **RC=0 且不进链接步骤** ⇒ 差别只在 `pkgtype`。官方 v0.10.4 说明已承认 native 库编译「仍在打磨」⇒ **别当未知 bug 提**；要提只提「早失败/清晰诊断 + 不毒化整模块」 |

| D4 | **判定型脚本的 fail loud** | 静默 `return nil` / 不查 `sc.Err()` / root 不存在也 `exit 0` 打印"0 条" | 与"真无重复"不可区分 ⇒ 违反项目纪律，要求 fail loud |

| D5 | **safe-delete 钩子会拦脚本的删除** | 探针每轮 `shutil.rmtree(输出目录)`（文件数 >50）⇒ stderr `[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":N,"threshold":50,"scope":"turn"}`，脚本 **RC=1** 整体失败；**同一 turn 内逐次删除也累计计数**（串行删单文件照样会在 ~50 次后触发） | 目录复位一律用 **`os.rename` 改名让位**（到 `*_old_<ns>`），语义等价（每轮仍是空目录）且不触钩子。见 `01-探针与对拍` 的探针写法 |

| D6 | **`subprocess(text=True)` 按系统 locale 解码 ⇒ 会话外必崩** | agent 会话里 python 带 `PYTHONUTF8=1` / `PYTHONIOENCODING=utf-8`（实测），探针跑得通；**在普通 cmd 窗口（GBK）跑同一探针**则子进程中文输出解码失败 ⇒ `UnicodeDecodeError: 'gbk' codec can't decode byte 0x..`，随后 `p.stdout` 为 `None` ⇒ `TypeError: 'NoneType' object is not subscriptable`，**整步崩掉**（2026-09-29 实测：8 步里崩了 4 步） | 要么在入口脚本里 `set PYTHONUTF8=1` + `set PYTHONIOENCODING=utf-8`，要么给每处 `subprocess` 显式 `encoding="utf-8", errors="replace"`。**⇒ 探针要交付给别人跑时，先在一个干净窗口试一遍**（本仓探针长期只在 agent 会话内跑，此缺陷直到 2026-09-29 首次外跑才暴露） |

## E · C / Clang 编译

| # | 坑 | 处置 |
|---|---|---|
| E1 | **msvc target 下不要加 `-lm`** | 会去找不存在的 `m.lib` 而链接失败；直接编即可 |
| E2 | **取 f64 位模式要 `memcpy`** | `%llu` 打无符号十进制，便于三方逐位对拍 |
| E3 | **`/O2` 与 `-O2` 不可互推** | 两个编译器的优化行为差异本身就是被测对象（见 B3） |
| E4 | **clang（msvc target）不认 MSYS 的 `/tmp/...` 路径（2026-10-10 补）** | `clang /tmp/probe/x.c` ⇒ `error: no such file or directory: '/tmp/probe/x.c'` + `error: no input files`；**配上 `\| head` / 管道后 `$?` 是尾命令的 0** ⇒ 极易读成"编译零诊断通过"（本机 clang 是原生 msvc 构建，不经 MSYS 路径翻译） | 传路径前一律 `cygpath -w`（或直接在仓库内建探针）；**判 clang 结论前先确认它真读到了文件**——裸命令取 rc，并检查 stderr 里有没有 `no input files`。同族：`python`（Windows 版）见 D1、`-` 开头的参数见 C2 |

## F · 文件与工作区安全

| # | 坑 | 说明 | 处置 |
|---|---|---|---|
| F1 | **`rm -f` 探针命令可能被提权出沙箱** | 会**真的删掉**工作区里的未跟踪文件；若这些文件被 `.gitignore` 覆盖，`git status` **报不出来** | 动任何文件前先 `cp` 到 `tmp/review_YYYYMMDD/`；命令失败时**不要**把后续步骤串在 `&&` 里（会漏掉还原分支）；收尾必 `git status --short -uall` + 逐文件字节核对 |
| F2 | **第三方并发改动** | 审阅期间工作区可能有别人正在写的文件 | **不属于审阅对象、也不该由你回滚**；判别用 `git show HEAD:`；报告里写明 |
| F3 | **复原要用精确路径** | `git checkout -- .` 会连别人的未提交改动一起清掉 | 只 `git checkout -- <具体文件>` |
| F4 | **裸 NUL 让整文件在 diff 里消失** | `.gitattributes` 的 `text eol=lf` **救不了含 NUL 的文件**（git 跳过转换） | 检查：`python -c "d=open(p,'rb').read(); print(d.count(b'\x00'))"`；处方 = 转义写法 |
| F5 | **CRLF / 编码问题一律看字节** | Read 工具渲染不可信（字面量、空白、不可见字符都可能显示错） | 涉字面量 / 裸 NUL / 非可见字符时 `hexdump` 或 `open(p,'rb')` |
| F6 | **后台任务输出接管道 = 日志截断 + 退出码双重失效** | 后台命令写成 `cargo test ... \| tail -40` 时：输出文件只剩尾部，全量统计（套件数 / passed / FAILED）事后无法补采；且任务上报的 exit code 是**管道尾命令（tail）的**——被测命令真失败也报 0，"后台全绿"结论不可信。是全域工具陷阱②（管道 `$?` 是尾命令退出码）与后台运行机制的组合形态，单看任一条都防不住 | 后台命令**禁接管道**、整条裸跑（输出文件自然完整落盘）；统计事后对日志文件 `grep "^test result:"` 逐列累加；确需精简就 `2>&1 \| tee 日志` + `set -o pipefail`（CI 同款）或改前台 |
| F7 | **并发在途改动污染门禁 ⇒ 判"这批绿不绿"必须用干净 HEAD** | F2 只说"别人的改动不属于审阅对象"，没说怎么在**不碰别人文件**的前提下拿到可信结论。实测形态：第三方正在做下一批（新增未跟踪源文件 + 改同包共享文件），该包测试由全绿变红，而**红点恰是上一批新增的锚** —— 看着像"这批把门禁搞红了"，实为在途代码 | 手法：`git worktree add --detach tmp/review_YYYYMMDD/headcheck <HEAD-sha>` → 在 worktree 里跑门禁（首跑全量编译，之后增量）→ `git worktree remove <dir> --force && git worktree prune`。worktree 落在 gitignore 目录即不污染主工作区状态；**别用 `git stash`**（会动别人的文件）。判据：干净 HEAD 绿 + 污染态红 = 在途副作用，报告里写明并归入"非审阅对象" |
| F8 | **`git checkout <commit> -- <files>` 会同时把 index 改成那个 commit 的版本** | 突变实验里用它把文件回退到 base 后，再 `git checkout -- <files>` 恢复的是 **index（base）** 而不是 HEAD ⇒ 工作树/构建产物悄悄停在旧版本，后续突变结论失真；`git status --short` 第一列 `M`（staged）即信号 | 突变实验前后一律先记 `git rev-parse HEAD`；还原用 `git reset --hard <HEAD>`（仅限自建 worktree 且确认无自有改动）或 `git restore --source=HEAD --staged --worktree -- <files>`；还原后重跑一次干净基线再下结论 |
| F9 | **还原源码 ≠ 还原产物：`scripts/bin/vitro` 的 js 臂不随源自动重建** | 突变注入后按字节还原源码（md5 已一致），再跑统一入口取样，读到的仍是**突变态**的 JS 产物——结论恰好是本该被证伪的那一版。native 臂有 stderr 新鲜度告警、vm_diff/protocol_frames 自带构建复核，js 臂没有等价门禁；且 `moon build` 增量判定依赖 mtime，`cp` 还原会把 mtime 推新但产物未必重建 | 每次还原后显式重建**所有会被消费的臂产物**再取样：`cd moonbit && moon build --release --target js cmd/vitro_js`（wasm/native 同理）；或直接用自带新鲜度门禁的闸（`protocol_frames` 等）取行为证据 |
| F10 | **判定型脚本的相对路径基准随 cwd 变 ⇒ 从子目录调用同一闸会假红** | 迁移批的门禁常把冻结基线 / 登记表放在**相对路径**下（如 `scripts/realcode_diff/gold_multifile.json`），解析相对**当前工作目录**而非脚本位置 ⇒ 同一闸从仓库根跑 exit 0、从子目录跑 exit 2（"金样本不可读"）。**在突变验证里这条会反向骗人**：子目录跑出的 exit 2 会被读成"突变被闸捕获"，而实际是基准没找到 | 突变验证时**连 cwd 一并复刻 CI 那一行**（闸的调用目录 + 相对入参），不另起"更方便"的目录；闸的输出须能区分「基准找不到」与「判红」两种 exit（前者文案里点路径）。自查：同一闸在两个 cwd 各跑一次，退出码不同即命中本条。实例：对账闸在子目录跑因基准路径重复拼接而 exit 2，一度把 16 个突变全判成"被捕获"，改用 CI 原样命令链后翻转（10 个仍绿——那才是真结果） |
| F11 | **actionlint 不校验 composite action 本体**（2026-10-30 审阅演化） | `actionlint .github/actions/setup-moonbit/action.yml` 把它当 workflow 扫 → 报 `"on"/"jobs" section is missing`，即**根本不校验 action 元数据**；实测把 run 步的 `shell:` 删掉后 `actionlint .github/workflows/ci.yml` 仍 rc=0（action 体内的违规在 workflow 声明面上不可见） | actionlint 的探针结论只覆盖 **input 面**（注入 `bogus_input` 会红），**body 面**（composite 每步必备 `shell`/`uses`）只能等 CI 首跑。审阅 action 改动时：手查每个 run 步的 `shell:`/`uses:` 字段，或写 5–10 行自断言；**勿把「已过 actionlint」读成「action 没问题」**——这一句要写进 action 头注 |
