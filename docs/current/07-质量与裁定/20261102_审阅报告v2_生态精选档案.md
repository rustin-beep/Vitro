## 一、R5a：mooncakes 生态作者地图（金矿地图）

### 一句话结论

### 关键结论（全量内联）

1. **依赖面真相**：0.9.1 发布源码包无 .mooncakes、moon.mod 无 deps——发布面零外部依赖；依赖真身在工作仓 `moonbit/.mooncakes/moonbitlang/x`（x@0.5.5 全家 18+ 包），**Vitro 实际只 vendored 消费 fs 子集 5 文件**（见 THIRD_PARTY.md）。
2. **作者版图**：moonbitlang 官方（x/core，vendored 血缘上游）；**marianoguerra = mooncakes 最活跃个人作者，17 个 MoonBit 仓（`-mb` 家族），2026-10 密集产出，Erlang 语言实现老兵（efene/efe 作者）**——GitHub API 拉全 100 仓元数据已落盘审阅现场；mizchi（js_core/js_browser/fswatch/x）、moonbit-community（html）、moonbitlang/skills（官方 agent skills 仓）只登记未 clone。

4. **上游修复时间线**：x@0.5.6（2026-10-20）decode 改 FFFD 替换并委托 core（与 vitro #363 方向一字不差）；x@0.5.7（2026-10-30）`to_utf8_bytes/to_utf8_string` 双双 `#deprecated`（指向 core `encode/decode_lossy`）——**vitro 的 vendor_baseline.json（0.5.5 内容哈希）将判漂移**，需决策：跟随 deprecation 换 core 依赖（破零依赖）vs 维持 vendored（语义已对齐）vs 豁免口径。
5. **core @utf8.encode 孤代理三后端分叉**（core `encoding/utf8/encode_js.mbt` 头注原文「Unpaired surrogates are replaced with U+FFFD, matching TextEncoder. **The other backends panic on them instead.**」）：js 臂走 TextEncoder（FFFD），native/wasm 臂 `abort("invalid surrogate pair")`——官方明知且文档化的分叉；凡 vitro 消费 core encode 的路径在三臂下需自防。
6. **x 的 CI 四件可整体搬进 Vitro**：pre-release moonc 前瞻检查；publish.yml 发布三件套（tag `v<version>` 必须指向当前 HEAD 防漂移、`moon info` 后 `git diff --exit-code` 接口面零意外、`moon package` 解压后再 `moon check --target all --deny-warn` 防「发布包缺文件」——0.9.0 断供事故同族风险的 CI 化拦截）。
7. **零依赖发布经济学金句**（wax lib/moon.mod 头注）：「THERE IS NO `import` BLOCK HERE, and that is the point——模块依赖会被每个消费者拉取，无论是否 import 用到它的包」——Vitro 零依赖路线的同业先例+理论依据。
8. **lib/dev 双 moon.mod 分离发布模式**（pure-py-mb）：`moon publish` 打包模块整棵目录树且 moon.mod 无 exclude——「发布库不带 832 个测试 fixtures 的唯一办法是让库自身成为模块」；Vitro 未来要把 corpus/教学资产从发布面剥离，这是标准答案。

## 三、R5e：同业 MoonBit 语言实现对照（wax-mb / pure-py-mb）

### 一句话结论
诊断「值」的设计（数据不携渲染、accumulate 不抛、稳定码位）三仓已同构收敛；Vitro 在治理（单源生成+闸工程+基线断言）与诊断教学域上明显领先同业，在**渲染面**（结构化消息/三格式渲染器）与**消费侧验证**（假想下游链接冒烟、桥唯一性断言、cram 行为回归）上存在同业已趟平的路线图。

### 关键结论（全量内联）

1. **wax-mb（wax@0.4.2）诊断族六包**：`basic`（前端错误值 Report，accumulate-don't-raise，仿 moonbitlang/parser）/ `message`（结构化消息组合子 Words/Atom/Raw/Seq/Sep/Group；头注「The tree carries the message's STRUCTURE; the theme and the width arrive only at render time」）/ `diagnostic`（结构化诊断值 + human/json/short 三渲染器分文件）/ `warning`（23 臂 enum + 稳定连字符名 + Policy 三级 Hidden/Displayed/ErrorLevel + `parse_spec` 解析 `-W name=level`）/ `colors` / `printer`。**wax 无数字错误码**：错误无 code，警告以名字为稳定标识。
2. **pure-py-mb（pure-py@0.12.0）**：`lib/error/` 三文件 + `Reason::code()` 稳定码 `purepy::<kebab>`（73 臂手写）+ `Reason::message()` 逐字复刻 Python f-strings（措辞被 conformance oracle 锁定）；**渲染全外包给独立发布的 `marianoguerra/error-report@0.1.1`**（根包纯值层「Nothing here renders anything」+ render/ 四渲染器 + style/）。
3. **口径冲突警报**：error-report 偏移口径是 **UTF-16 code unit**，与 Vitro「偏移/长度一律字节口径」裁定**正好相反**——跨包接入必须显式转换。
4. **error-report 预拆仓纪律**（moon.mod 头注）：「written to be lifted out … must never name that consumer, and it must never grow a dependency. `tools/boundary-check.sh` enforces both」——为将来一键拆仓提前用 CI 锁两条不变量。
5. **conformance 隔离**：pure-py `test/conformance/` 逐字 vendored 规范自带测试集、归属 dev module **不随库发布**（moon.mod 无 private 字段，「Never published」是规则不是机制，防误发做成 publish.sh 只接受 lib/cli 两参数）；**Vitro 已等价达成**（corpus 1102 文件在 module 目录树之外）。
6. **双向 ratchet**（conform-policy.json）：「A ratchet, not a target——fails when an oracle drops below its floor (a regression) **and equally when it rises above one (an improvement nobody recorded)**: rerun with --regen-policy and commit the moved floor in the change that earned it.」——**升过顶也红**；「改善也须登记」Vitro facts 规则集可吸收。
7. **Vitro corpus 分桶实测对照**：baseline 534 / knr 110 / leetcode 138 / llm_multifile 112 / cpp 83 / template_generated 83 / gap 23 / codegen_skeleton 13 / llm_scale 6 / mutator_probe 1；Vitro 按**来源**分桶，pure-py 按**oracle 裁定**分桶（succeeds/raises/rejects）。
8. **闸形态对照**：pure-py `boundary-check.sh` 80 行 POSIX sh 四条 grep 白名单（含**桥唯一性——适配器文件数 >1 即红 =0 也红**）；wax 无此闸（「Reported, never gated」）；**Vitro pkg_deps（310 行 .mts + rules.json 数值分层 L0–L9 + 越层/环/未登记/空集四判据 + selftest + node:test）工程强度全面占优**，但缺两条同业语义：**桥唯一性断言**与 **embed-smoke 消费侧冒烟**（workspace 外假想消费者编译冒烟；wax 量化收益：约 15k 行 LR 表不会被 codegen 消费者编译）。
9. **测试形态数字（亲跑统计）**：wax 53 个 _test.mbt / **1** 个 _wbtest（test 块 532 黑盒 / 25 白盒）；pure-py 26 / **1**（190/6）；Vitro 14 / **90**（156/**985**）——同业黑盒 95%/97%，**Vitro 白盒 86%**，方向完全相反。同业白盒义务：头注 20 行写明「为什么这段测试不能黑盒」。Vitro 独有数量基线断言文化（diag_wbtest coverage_baseline）。
10. **wax 三层回归**：corpus 2010 模块（manifest.json 313KB 逐文件记 origin 出处）+ golden（index.json 448KB pin 哈希入档）+ **cram 103 个 .t**（参考实现 CLI 测试直接跑——exit code/stdout/stderr 分流）。Vitro 的 vitro_cli_smoke 覆盖同形性但不覆盖「rc 值表 × flag 组合」行为快照（Vitro 是 spec 驱动 + protocol_frames 闸，形态不同）。
11. **pure-py 七 oracle + 种子化模糊**：七 oracle 对 CPython 逐行 1005/1005；`tools/fuzz.py --count 2000 --seed 1`（种子固定可复现——回归意义而非发现意义，进 CI）；golden 纪律金句：「**Goldens are regenerated, never edited.** … Editing one by hand turns a disagreement into a silence.」；wax 对应句：「Do not 'fix' a golden file to make a test pass; a golden diff means either you changed behaviour or upstream did, and both need explaining.」
12. **moon 工具链发布陷阱两条**（Vitro 未来拆多 module 发布必踩）：①wax `publish-dry.sh`：**`moon publish --dry-run` exits 255 on a dry run the SERVER ACCEPTED**——「the acceptance line is what is believed here, not the status」；②pure-py `publish.sh`：连坐发布的 registry index 竞态——「a second after `lib` went up, it still predates it. ## 五、R5h：mooncakes registry 断供机制链源码补全

### 一句话结论
0.9.0 断供事故的机制链已逐环节源码定位：registry 从 `moon add` 到 `moon build` 的 A–G 七环节里，「moonc 版本约束」在**哪一层都不生效**（moon.mod schema、索引行、解析结果、服务端 manifest 四层结构全部无工具链字段；core 随 moonc 本地分发不走 registry；服务端构建只是发布后异步的文档快照），断供发生在且只发生在环节 G（本地构建）——「加得下、建不起」，而 0.9.1 修复的实际载体就是 latest 指针移动。

### 关键结论（全量内联）

1. **默认 endpoint 三件**（moonutil `RegistryConfig`）：api=`https://mooncakes.io`、index=`https://mooncakes.io/git/index`、download=`https://download.mooncakes.io`；覆盖序 `~/.moon/config.json` → `MOONCAKES_REGISTRY` 环境变量。
2. **「公开索引仓停更」的准确定位**：GitHub mooncakes.io-index 只是镜像快照，**真源是 `https://mooncakes.io/git/index` 的 git smart-HTTP 服务**（探针实证活体：当日仍有新提交内容）；默认 MetadataBackend 是 Git(GitIndex)（首装 shallow clone + 后续 fetch/reset，四因自愈重克隆）；`MOON_REGISTRY_API=1` 才走 HTTP metadata。
3. **索引行 schema**（`~/.moon/registry/index/user/vitro/engine.index` JSONL 每版本一行）：字段 `{version, deps, checksum, yanked, yanked_reason}`——**仅此五类，无任何工具链/moonc 字段**。
4. **版本解析**：不带版本 = 取 BTreeMap 尾键——**semver 最大即 latest，不读服务端 latest 字段**；带版本 = Go 式 MVS；解析错误类型全景（ModuleMissing/VersionMissing/NoSatisfiedVersion/ConflictingVersions/RegistryReadFailed）**全部是坐标/版本类，不存在工具链兼容类错误**。
5. **core 特例注入**（resolver.rs `inject_std`）：moonbitlang/core **不走 registry**，从本地 moonc 安装目录直接读 moon.mod 注入依赖图——**core 的版本 = 本地工具链版本，无独立版本约束**；moonc 升级 = 所有下游 core 静默换代。这是 0.9.0 事故的结构性支点。
6. **checksum 三道校验 + 不可变铁律**：索引行 SHA-256 → 下载流式校验 → **cache 命中重校验**；历史实锤注释（dependency_source.rs 测试）：`lijunchen/hello18@0.1.30` 发布后被换过包——「registry 版本不可变，checksum 变了即拒，想接受需显式 `moon clean --dep-cache`」；**checksum 入 registry 后不可覆盖，发错只能递增版本**。
7. **发布侧闭源**：moon publish/package/deprecate 的实现不在开源 mooncake crate 里，委托外部 `mooncake` 可执行文件（参数经 stdin JSON）——只能行为面实证：dry-run = 本地构建 Check passed + 服务端查重 409「Version Error: duplicated」（release_preflight 判据来源）。
8. **0.9.0 断供环节定位：G（且只有 G）**：moonc ≥0.10.18 删 `core/abort`，0.9.0 包内 time_travel 仍 import → A–F 全部健康（`moon add` 零报错），环节 G 编译红——**「加得下、建不起」；registry 交付完整性（字节级）与构建兼容性（语义级）正交，registry 只保前者**。
9. **根因三层**：①schema 层无表达位（moon.mod 全字段清点无 toolchain/moonc 字段，索引行/解析结果/服务端 manifest 同）；②core 分发模型（见 5）；③**服务端构建时点固化**——registry 确实跑构建（`/api/v0/builds` 队列）但那是发布后异步的**文档构建**，构建失败也不阻断（官方文案：「Documentation failed to generate... **The package is ready to install and use as a dependency**」）。
10. **为什么 0.9.0 在架时 Vitro CI 绿而下游红**：同一份 zip（checksum 逐位一致）在两种工具链下健康状态不同——Vitro CI moon/moonc exact pin，下游用户 moon 自动更新 ≥0.10.18 → 红。**发布者验证环境 ≠ 下游构建环境，registry 不做两者的桥。**
11. **0.9.1 修复机制**：不是 moon.mod 兼容面调整（无字段可调），而是**递增版本重发**——代码侧治本（包内去除 core/abort 引用链）+ 新索引行 + 新 checksum（`f6ef9b34…`→`51d62540…`）+ 新 zip；**修复的实际载体 = latest 指针移动**。**诚实披露：0.9.0 永久断供**——索引行不可覆盖、`yanked:false` 仍在架，显式 `moon add vitro/engine@0.9.0` 依然会红；且 yanked 本身只是 advisory（deprecated releases remain eligible for version selection）。
12. **registry 侧「下游可构建性预检」确认不存在**（四源证据：客户端全链零工具链检查点/服务端构建失败不阻断/0.9.0 build_status:"success" 与新 moonc 必红并存/服务端构建日志 0 errors 是文档资产）。可用但不构成防线的信号面：manifest 的 `build_status` 与 `created_at`（发布时点快照，可发版后核对）；共同盲区：**工具链演进后不重跑**。
13. **顺带发现另一类断供形态：索引源错配**——下游误配 GitHub 停更镜像为 index 表现为「永远查不到新版本」的软断供，Git 索引后端对 remote 不匹配自动重克隆到配置 URL，错配即固化。Vitro 侧无法设防，排查参考（下游「add 不到新版」先查 index 配置）。
14. **mooncakes.io 前端 index.html 给 agent 留了官方 API note**（「别爬渲染页，用这些 endpoint」）；12 组 curl 探针全程**零 zip GET**（反刷量约束）；平台总量实测 3517 模块 / 31442 包 / 56M 行 / 10.5M 下载；`module_index.json` 发布后 **~18s 就绪**；`symbols.zip` **404**（best-effort 线路不存在，彩排工具勿依赖）；`summary_version` 可能滞后（实测 cmd/dump_ast 摘要停 0.9.0 且 `is_summary_current:false`）。
15. **好话定性**：Vitro 侧 0.9.0 事故响应教科书级——六天定位（#402 dry-run 二分实证）→ 0.9.1 重发 + release_preflight 闸 + playbook 验收条目升级（「只验 add 不验 build 等于没验」）；mooncake crate 防御纵深（absence vs failure vs denial 三分语义写进 trait 契约、token 只走 stdin）。

| G 本地构建 | **`moon publish --dry-run` 的 Check passed**（release 档） | **本机单一工具链** |
| 下游真实环境 | **干净消费工程 moon add + 双目标 build**（playbook 人工一次，反刷量不进 CI） | 下游 moonc 异构 |

**防线闭环组合**（报告 3.2 原句）：release_preflight 的 dry-run 是「下游模拟」的合理近似——能抓已发生的工具链升级；**永远抓不到发布后未来工具链删符号（无机制可预知）**——正确防线是**工具链升级时的在架复检**，已由 toolchain_probe + 升级后「moon add 在架版 + build」复验承担，**两者组合即闭环：preflight 守发布时点、toolchain_probe 守在架期**。
