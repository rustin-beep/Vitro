# 工具链与踩坑

> 环境 / 工具链的**确定性行为**与已知假绿假红来源。撞到报错先查这里，**别急着判"代码有问题"**。
>
> 写入规则见 [`05-演化机制.md`](05-演化机制.md)：只写"下次还会遇到"的，不写一次性现场。

## A · MoonBit 工具链

| # | 坑 | 表现 | 处置 |
|---|---|---|---|
| A1 | **`moon check` 偶发文件锁冲突** | `Sys_error("...\\_build\\...\\*.ast: Permission denied")`，整轮报 `failed to run check for targets [...]` —— Windows AV / Defender 抢 `_build` 文件锁 | **直接重试一次**即绿，与代码无关；**别据此判"构建失败"**（多次实证） |
| A2 | **缺 `moon.pkg` 的目录不被视为包 ⇒ 静默成功** | `moon build --target native <dir>`：零输出、**EXIT=0、零产物**；`check` 同样静默（`no work to do`） | `<dir>` 是**目录过滤器**，判包依据 = **该目录有无 `moon.pkg`**。⇒ **别拿 EXIT=0 当成功**，要 `find _build -name "*.exe"` 验证产物 |
| A3 | **`moon.pkg` 内容必须是合法变体** | `pkgtype(kind: "lib")` ⇒ `unknown variant 'lib', expected one of library, executable, foreign_library`；空文件 = 默认 library ⇒ `fn main` 报 `[4069] Unexpected main function in the non-main package` | 可执行工程写 `pkgtype(kind: "executable")` |
| A4 | **`moon test` 失败不打印实际值** | 只报 `FAILED` 行 | 用 `fail(s)` 把实际值打出来（`assert_eq` 失败不含值） |
| A5 | **增量编译漏检** | 连续快速改写同一文件，工具链可能复用旧产物（Windows 同秒时间戳）⇒ 假绿 / 假红 | 注入与测试之间 **`sleep ≥1.5s`**；首轮结果不可信时重做 |
| A6 | **`moon fmt --check` 本机 exit 127** | `failed to execute git --no-pager diff --no-index` | **别把 127 读成"格式没问题"**。CI 口径是 `moon fmt` + `git diff --exit-code`，见 `02` 的 D13 |
| A7 | **`moon test -p <pkg>` 的 Total 是单包数** | 与全仓总数对不上 | 先确认口径再判错；往包里加探针文件会让它 +1，**记得从基线里减掉** |
| A8 | **`moon check` / `moon test` 不会顺手刷新 `.mbti`** | 跑完 `git status` 仍干净 | ⇒ CI 里 `mbti_sync -check` 的顺序判据可信（这是**要实测**的结论，别假设前面的步骤会顺手修好） |
| A9 | **区间语法** | `for _ in 0..3` 报 `Missing '=' after '..'` | 写 `0..<3`（或 `0..=2`） |
| A10 | **浮点字面量必须带小数点** | `1e23` 语法错 | `1.0e23` |
| A11 | **core 包要显式 import** | 用 `@env` / `@fs` 只警告但会连带报错 | 在 `moon.pkg` 的 `import { "moonbitlang/core/env" }` 里声明 |
| A12 | **`raise` 需真 error 类型** | `raise "字符串"` 编译错（`String is not an error type`）；`fn main raise` 不允许 | 声明 `priv suberror E { Fail(message~ : String) }`；入口用 `fn main` + `try/catch` |
| A13 | **dump 类工具"成功"也可能失败** | CLI 打印成功但产物里 `ok:false` | 必查产物的 `ok` 字段 |
| A14 | **`String::length()` 是 UTF-16 码元数，不是 UTF-8 字节数** | `@utf8.encode(s)[:s.length()-1]` 会切进多字节序列 ⇒ `decode` 抛错 ⇒ `catch { _ => "" }` **静默产空串** | 用 `let b=@utf8.encode(s); @utf8.decode(b[:b.length()-1])` |
| A15 | **扫描 / 统计脚本必须排除 `_build`** | `__generated_driver_for_*_test.mbt` 含大量重复 | 否则把生成代码误判成"自研代码重复" |
| A16 | **`moon check` warning 数量可当回归信号** | 不卡 CI，故容易被忽略 | 审"修复批"时比改前 / 改后总数，把增量落到 `文件:行` |

| A17 | **`moon.mod` 的 `import` 必须带版本号** | `import { "vitro/engine" }` ⇒ `Failed to resolve the module dependency graph: moon.mod only supports versioned registry dependencies` | 接**本地工作区**当依赖：写 `"vitro/engine@<本地 moon.mod 的 version>"` + 在 `.mooncakes/<owner>/<mod>` 建**目录联接**指向本地模块目录（PowerShell `New-Item -ItemType Junction`）。实测可编到本地 HEAD 码（2026-09-29） |

## B · 构建与工作目录

| # | 坑 | 处置 |
|---|---|---|
| B1 | **构建命令必须在 `moonbit/` 下跑** | 仓库根跑 `moon build --target native cmd/run` = `Error: not in a Moon project`（exit 127）。脚本自己的报错提示可能照抄这条错命令 ⇒ "构建失败但工具照跑旧 exe" |
| B2 | **runner exe 的新鲜度无人校验** | 跑依赖 runner 的防线前**先手动构建**；`_build/.../cmd/run/run.exe` 的 mtime 可能早于其源码 |
| B3 | **大常量表会砸进单个 `moonbit_init`** | 编译器把整个模块的全局初始化发射成一个平坦函数；大数组字面量会展开成 N 条逐元素 store。⇒ Windows 默认 `cl` 在高优化级别下会在该函数上撞优化器悬崖，而 `clang` 不会。`MOON_CC=clang` 可绕过；文件大小无关，**病在单函数语句数** |

| B4 | **全量 `moon build --release --target native` 会被 `foreign_library` + `+native` 的包卡死** | `gateway` 报 `LINK : fatal error LNK1561: 必须定义入口点`（native 后端对它仍去链可执行文件），整轮 `Failed with N warnings, 0 errors` → `failed to run build for target Native`；同期 `cmd/*` 全部正常 | 先看是不是**只有该包红**；构建改用**逐目标**形态（`moon build --release --target native cmd/run` …）。CI 若只跑该包的 wasm-gc 形态，`+native` 声明就从未被验证（2026-09-29 实锤：gateway + CI 只跑 `--target wasm-gc gateway`） |

| B5 | **`foreign_library` 包单独做 native 构建必失败** | `moon build --release --target native <fl_pkg>` ⇒ `LINK : fatal error LNK1561: 必须定义入口点`（moon 对它仍去链可执行文件），整轮 `Failed with N warnings, 0 errors` → `failed to run build for target Native`；**4 行最小模块即可复现**（与代码规模/警告数无关）。消费者（executable 导入它）**不受影响** | 两条直觉修法已实测证伪：①去 `+native` ⇒ 消费者报 `Selected backend 'native' is incompatible with the dependency graph`；②改 `pkgtype(kind: "library")` ⇒ `[4219] #export_name 只能用于 foreign library`。**可用修法 = 拆包**：核心逻辑放 `library` 包（双 target），另建只含 `#export_name` 面的 `foreign_library` 外壳（`+wasm-gc` 单目标）——全量 native 构建与 wasm 导出面同时成立（2026-09-29 实测三态全过）。**补充**：与编译器无关（`MOON_CC=clang` 下同样失败，只换成 `lld-link: error: subsystem must be defined`）；**爆炸半径 = 整个模块**（模块里只要有一个没人链接的 foreign_library，模块级 `moon build --target native` 就整体失败）；对照纯 `library` 包单独构建 **RC=0 且不进链接步骤** ⇒ 差别只在 `pkgtype`。官方 v0.10.4 说明已承认 native 库编译「仍在打磨」⇒ **别当未知 bug 提**；要提只提「早失败/清晰诊断 + 不毒化整模块」 |

## C · Shell / 命令行（msys on Windows）

| # | 坑 | 表现 | 处置 |
|---|---|---|---|
| C1 | **bash 常丢 PATH** | 命令找不到 | 前缀 `export PATH="/usr/bin:/bin:$HOME/.moon/bin:$PATH"` |
| C2 | **msys 把 `-` 开头的参数当路径转换** | `/O2` 被转换 | 用 `-O2`，或 `MSYS_NO_PATHCONV=1` |
| C3 | **`\| head` 会 SIGPIPE 杀编译器** | 判"构建失败"前必须 tail 全量输出 | 别用 `\| head` 截断构建输出 |
| C4 | **管道 `$?` 是尾命令的退出码** | 误判脚本成败 | 用 `PIPESTATUS`，或裸命令取值 |
| C5 | **Windows 路径的 grep 过滤** | 反斜杠漏匹配 | 写 `[/\\]` 双兼容 |
| C6 | **`git check-ignore` 是唯一可靠的忽略判定** | 凭 `.gitignore` 文本推断会错（尤其父目录被忽略时，`!` 放行子目录**不生效**） | 用 `git check-ignore -v <path>` 实测 |
| C7 | **`git ls-files --eol` 报工作区态** | `w/-text` ≠ 文件真的不可 diff | 结合 `git diff` 实测；`attr/text` 仍会给文本 diff，**别从 grep 的 binary 判定推 git 的可见性** |

| C8 | **本机进程启动开销可达 ~150 ms（环境级，不是沙箱）** | 同一 `vitro_cli.exe` 二进制 2026-09-26 记 5.8 ms、2026-09-29 实测 **146 ms**；旧探针 exe 12 ms → 193 ms；`dangerouslyDisableSandbox` 复测无改善 ⇒ 机器级（该日 `Defender RealTime/BehaviorMonitor/TamperProtected` 全开 + 第三方滤镜驱动候选）。泄流型工具另有**每文件写盘税**（dump 类每轮写 366–732 个文件） | **「每次调用起一个进程」的绝对性能数字该日不可引用**；改用**同进程内重复 + 空转场景自校准**（`wasm_bench` 形态——加数与减数同源 ⇒ 开销对消）。**勿用固定常数扣启动**：该值在 140–190 ms 间漂移 ±30%，<500 ms 的测量做减法会翻符号 |
| C9 | **MSYS bash 的 fork 本身很贵** | `ls` ×10 在 bash 循环里实测 ~350 ms/次级别 | 别用 `date +%s%N` 包 bash 循环测进程启动——测到的是 MSYS 的账，不是被测程序的 |

| C10 | **性能探针的「空转基线」必须与被测场景同轮次交替测** | 整轮只测一次空转，若该开销在 run 内漂移，**全部场景的「扣启动」结果跟着漂**：实测同一 0.5.0 二进制同小时三次，parser 纯算 0.67/1.42/0.67（**2× 抖动**），某轮甚至把 lexer 纯算压成 2.4ms（真值 ~37ms）⇒ 整轮作废 | 驱动器改成**每个场景前后各测一次空转、取两次均值作该场景基线**，并打印前后差值（drift）当健康度指标（改后 drift 中位 ±2-5ms）。**信噪比红线：扣启动后的纯算 <100ms 的场景，比值不可引用** |
| C11 | **进程启动开销的归因法：在 main 入口打时间戳** | 只知「启动慢」不知花在哪 | 写一个在 main 入口打印 `time.Now()` 的探针（Go 最省事），父进程记 t0/t1，即可把开销拆成 **CreateProcess 本身 / 进 main 之前 / 退 main 之后** 三段（2026-09-29 实测：22.6ms / ~125ms / 3ms ⇒ 病灶在映像加载与校验，不在退出路径也不在程序计算——空 main 一样付）。配套做**尺寸无关性**（微型自编 exe vs 7MB 现成 exe）与**父进程无关性**（python 父 vs PowerShell 父）两个对照 |

| C12 | **本 agent 会话内的进程创建慢 ~145ms（机器本身正常）** | 会话内：任意 exe 启动 145-151ms、尺寸/签名/父进程（python、MSYS bash、PS）都无关、无预热收敛、`CreateProcess` 22ms + **进 main 之前 ~125ms**；**同一分钟在普通 cmd 窗口同一脚本只有 4.6-6.0ms**（`CreateProcess` 1.7ms / 进 main 前 5.0ms / 退 main 后 1.3ms）| ⇒ **性能测试里的「每次调用起一个进程」口径绝不能在 agent 会话内采集**；也别据此归因到 Defender/VBS/HVCI（那些两侧相同）。会话内绕不过：`CREATE_NO_WINDOW` 更慢、`CREATE_NEW_CONSOLE` 490ms、`dangerouslyDisableSandbox` 无效、WMI `Win32_Process.Create`/`Start-Process`/`cmd /c` 被工具策略拦 ⇒ **交给用户在普通窗口跑**（2026-09-29 实测定案）|

## D · Python / 脚本

| # | 坑 | 表现 | 处置 |
|---|---|---|---|
| D1 | **本机 `python` 是 Windows 版** | 传 `/tmp/x` ⇒ `FileNotFoundError` | 产物先写到**仓库内路径**再交给 python |
| D2 | **文本模式写文件会把 LF 变 CRLF** | 改写源码后整文件变 CRLF，`git status` 脏一片 | 改写源码一律用**二进制模式**或 `newline=''` |
| D3 | **`json.loads` 再 `dumps` 会改写成 repr** | 取浮点真值时值被改写 | 取 **原始响应文本**（正则 `"value":\s*([^,}]+)`） |
| D4 | **判定型脚本的 fail loud** | 静默 `return nil` / 不查 `sc.Err()` / root 不存在也 `exit 0` 打印"0 条" | 与"真无重复"不可区分 ⇒ 违反项目纪律，要求 fail loud |

| D5 | **safe-delete 钩子会拦脚本的删除** | 探针每轮 `shutil.rmtree(输出目录)`（文件数 >50）⇒ stderr `[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":N,"threshold":50,"scope":"turn"}`，脚本 **RC=1** 整体失败；**同一 turn 内逐次删除也累计计数**（串行删单文件照样会在 ~50 次后触发） | 目录复位一律用 **`os.rename` 改名让位**（到 `*_old_<ns>`），语义等价（每轮仍是空目录）且不触钩子。见 `01-探针与对拍` 的探针写法 |

| D5 | **safe-delete 钩子会拦脚本的删除** | 探针每轮 `shutil.rmtree(输出目录)`（文件数 >50）⇒ stderr `[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":N,"threshold":50,"scope":"turn"}`，脚本 **RC=1** 整体失败；**同一 turn 内逐次删除也累计计数**（串行删单文件照样会在 ~50 次后触发） | 目录复位一律用 **`os.rename` 改名让位**（到 `*_old_<ns>`），语义等价（每轮仍是空目录）且不触钩子。见 `01-探针与对拍` 的探针写法 |
| D6 | **`subprocess(text=True)` 按系统 locale 解码 ⇒ 会话外必崩** | agent 会话里 python 带 `PYTHONUTF8=1` / `PYTHONIOENCODING=utf-8`（实测），探针跑得通；**在普通 cmd 窗口（GBK）跑同一探针**则子进程中文输出解码失败 ⇒ `UnicodeDecodeError: 'gbk' codec can't decode byte 0x..`，随后 `p.stdout` 为 `None` ⇒ `TypeError: 'NoneType' object is not subscriptable`，**整步崩掉**（2026-09-29 实测：8 步里崩了 4 步） | 要么在入口脚本里 `set PYTHONUTF8=1` + `set PYTHONIOENCODING=utf-8`，要么给每处 `subprocess` 显式 `encoding="utf-8", errors="replace"`。**⇒ 探针要交付给别人跑时，先在一个干净窗口试一遍**（本仓探针长期只在 agent 会话内跑，此缺陷直到 2026-09-29 首次外跑才暴露） |

## E · C / Clang 编译

| # | 坑 | 处置 |
|---|---|---|
| E1 | **msvc target 下不要加 `-lm`** | 会去找不存在的 `m.lib` 而链接失败；直接编即可 |

## F · 文件与工作区安全

| # | 坑 | 说明 | 处置 |
|---|---|---|---|
| F1 | **`rm -f` 探针命令可能被提权出沙箱** | 会**真的删掉**工作区里的未跟踪文件；若这些文件被 `.gitignore` 覆盖，`git status` **报不出来** | 动任何文件前先 `cp` 到 `tmp/review_YYYYMMDD/`；命令失败时**不要**把后续步骤串在 `&&` 里（会漏掉还原分支）；收尾必 `git status --short -uall` + 逐文件字节核对 |
| F2 | **第三方并发改动** | 审阅期间工作区可能有别人正在写的文件 | **不属于审阅对象、也不该由你回滚**；判别用 `git show HEAD:`；报告里写明 |
| F3 | **复原要用精确路径** | `git checkout -- .` 会连别人的未提交改动一起清掉 | 只 `git checkout -- <具体文件>` |
| F4 | **裸 NUL 让整文件在 diff 里消失** | `.gitattributes` 的 `text eol=lf` **救不了含 NUL 的文件**（git 跳过转换） | 检查：`python -c "d=open(p,'rb').read(); print(d.count(b'\x00'))"`；处方 = 转义写法 |
| F5 | **CRLF / 编码问题一律看字节** | Read 工具渲染不可信（字面量、空白、不可见字符都可能显示错） | 涉字面量 / 裸 NUL / 非可见字符时 `hexdump` 或 `open(p,'rb')` |
